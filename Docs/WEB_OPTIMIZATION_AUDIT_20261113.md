Два меша замковых гирлянд содержат **352 260 вершин**: Warm Light — 255 440, Ruby — 96 820. Сумма сериализованного `m_DataSize` — **19 726 560 байт**. Это размер vertex data этих источников, а не обещанная экономия ZIP или точное потребление памяти Web. Крупные Snow Hill и Signal Mountain также требуют разбора геометрии.

Порядок исправления: выделить игровые варианты без ненужных выключенных альтернатив; упростить геометрию ламп, снега и мелкого декора; затем проверить коллайдеры, дальние LOD и тени. Не объединять в один огромный меш весь город: это может ухудшить отсечение, локальную выгрузку и обслуживание интерактивных объектов. Сохранять GUID, стабильные ключи, точки предметов/охраны, поверхности и привязки магазинов. WorldSpawnIdentity.StablePath использует sibling index: удаление соседней ветви может изменить идентичность, даже если сам предмет не двигали. Нужна проверка ключей и при необходимости явная версия совместимости. Проверить визуальное совпадение до и после.

Ранее найденные 14 пустых ссылок на меши у семи ProBuilder sources (7 MeshFilter и 7 MeshCollider) не считаются поломкой: обычные preview-клоны уже получили корректные меши через Awake. Эти семь процедурных объектов малы; само наличие ProBuilder не доказывает, что он главный источник нагрузки. Убирать его можно только после сохранения и проверки рабочих игровых мешей.

## 2. Догоняющая загрузка и выгрузка мира

В `CitySpawner.Update` сначала вызывается `SpawnCityAt` с полным Instantiate, затем город за `rear` удаляется. При восстановлении далеко по маршруту это создаёт ненужную работу. Модель ветвления при front=40 000, rear=38 000 и шаге Event 5000 сначала проходит семь городов 5000…35 000, уже оставшихся сзади. Это **семь лишних конструкций по 11 197 узлов**, распределённых по обновлениям; не один измеренный кадр и не замер времени восстановления.

Нужен пропуск заведомо ненужной геометрии до Instantiate с сохранением индексов, distance, RNG, ключей и сетевых состояний. Не пропускать мир около другого живого участника или точки возрождения. Покупки, переносимые/прикреплённые предметы, dropped loot и враги должны восстанавливаться по каноническим записям, а не повторной случайной генерации.

`WorldStreamingBudget` ограничивает число стартов аудита, но не длительность одного Instantiate. В `WorldCityStreaming` ещё есть повторный сбор Renderer/bounds города; у `WorldRegionStreaming` уже есть cache/быстрая проверка anchor. У `DecorationSpawner` проверка пересечений снова ищет ZoneCleaner и обходит Renderer размещённого декора. Следующий этап — кэш с корректной инвалидизацией при выгрузке и переносе начала координат, а затем измерение тяжёлого восстановления.

Стартовый авторский город уже включён в LevelEvent и загружается со сценой. Его root не зарегистрирован в текущем механизме WorldCityRegion/WorldRegionStreaming; `RegisterAuthoredItems` учитывает предметы, а не всю геометрию. Это отдельная задача включения авторского root в безопасную residency policy, а не доказательство, что ни один его объект никогда не удаляется.

Мёртвый игрок и игрок во время рекламы намеренно удерживают точку возрождения. Отключившиеся/покинувшие участники отфильтровываются; проверен флаг удаления аватара при уходе authority. Оснований объявлять это утечкой отключившихся игроков нет. Предыдущий длинный Editor-маршрут DB-ON-125 остаётся непринят по плавности; его результаты не заменены новым construction audit.

## 3. Размер загрузки и ранние зависимости

В build settings включены LoadingScene, Lobby, Forest, Desert, Winter, FirstRunAuthored и LevelEvent. Playable builder берёт все enabled scenes. В графе присутствуют 158 runtime Resources roots. Их объединённая зависимость — 969 путей / 78,608 МиБ исходников; **эта сумма пересекается с графами сцен** и не прибавляется к общим 400,814 МиБ. Только от LevelEvent зависят 280 путей / 143,052 МиБ исходников. Это полезный кандидат на разделение, а не столько же байт будущей экономии.

Скрытие Event кнопки не исключает его ассеты из сборки. Для выборочной загрузки нужен отдельный content provider на bundles/Addressables и удаление прямых включающих ссылок из стартового графа. Не просто перемещение папки. Resources входят в Player даже без прямого использования; это ограничение системы описано в [документации Unity](https://docs.unity.com/en-us/engine/6000.3/manual/assets-and-media/assets-managing-runtime/assets-resources-system/loading-resourcesat-runtime).

LoadingCollection держит Managers, Player и Canvas. Через ItemsManager → All.asset приходят ссылки на 87 предметов. Сам небольшой цикл из 87 элементов не назван узким местом без профиля; проверить нужно раннюю загрузку моделей/материалов и глобальные recovery-каталоги. Metadata/стабильные ID можно держать отдельно от тяжёлого визуала. При разделении нужны версия контента, доступность выбранной темы у всего экипажа, обработка неудачной загрузки и старых recovery tickets; связано с DB-ON-262. Социальный UI и скрытый HUD также кандидаты на ленивое создание, но пока не измерены как основные расходы.

В Web распакованный `.data` остаётся в виртуальной файловой системе браузера, а кэш помогает следующим входам. Выгрузка GameObject не удаляет автоматически исходный `.data`. Управляемая загрузка bundles может уменьшить начальную загрузку и этот объём. Это архитектурная рекомендация по [памяти Unity Web](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/webgl/develop/memory), а не доказанная экономия текущей игры.

FEEL занимает около 411 МиБ исходной папки, но native граф включает из неё **21 путь / 0,785 МиБ исходников**; в том числе debug Resources и шрифт Lato. Это не размер его скомпилированного кода в WASM. Архивы `.unitypackage` в граф не вошли. Workshop-named ресурсы есть в игровых зависимостях: 415 путей / 22,915 МиБ исходников. Их название не означает, что они не используются. Удаление целых FEEL/Workshop папок не является обоснованной оптимизацией.

## 5. Повторные CPU/GC операции и ожидания

- **EventSystemGuard:** EnsureSingleEventSystem вызывается в Update и LateUpdate. Оба пути ищут объекты по сцене и создают массивы через FindObjectsByType + LINQ. Нужны cache, scene events и редкая восстановительная проверка с сохранением SafeEventSystemInput и поведения DB-ON-055/058.
- **Solo fallback:** SharedRunRecovery каждые 2 секунды вызывает SharedSoloSnapshot.Capture даже без изменений мира. Создаются List/HashSet, обходятся текущие canonical items/enemies/pages, выполняются ToArray. Это O(N) текущих записей; копирование всего выгруженного архива или утечка не доказаны. Нужны версии/переиспользование, сохранив актуальное «Продолжить одному» при потере сети.
- **Начальная позиция лодки:** SetSavePosition около секунды вызывает Teleport каждый кадр; Teleport создаёт coroutine/WaitForSeconds. Можно убрать повторные временные объекты, но сам маршрутный прогон нельзя удалять без проверки восстановления генерации.
- **LoadingCollection:** ждёт WaitForProviders и включает группу объектов разом; собственного ограниченного ожидания/повтора нет. Внутренний timeout SDK не установлен чтением нашего кода. SDK не менять.
- **GameLoader:** после активации сцены без предельного срока ждёт BoardController.StartGame, пишет warning раз в 10 секунд. Нужен экран контролируемого отказа/повтора вместо вечного прогресса, без запуска неготового мира.
- **Социальные функции:** некоторые SDK await удерживают UI/semaphore без игрового timeout. Это риск зависшего социального действия, а не доказанная блокировка всего первого входа. Photon start/join/shutdown timeouts уже есть; они не требуют переписывания «заодно».

Scaled-time зависание DB-ON-054 уже исправлялось: загрузочный кадр перед LoadSceneAsync, unscaled ожидания лодки и UI существуют. FEEL HUD обновляется по изменениям с частотой 10 Гц; feedback не создаёт камеру/частицы на каждый удар. Эти старые решения не выданы за новые проблемы.

## Проверки после исправлений

ИИ сначала сравнивает одинаковые seed/route/контент до и после каждого изменения. Проверяются solo, 4 участника, late join, бывший хост, origin shift, split/caught-up, потеря сети → solo, возвращение в выгруженный город. Пропуск/оптимизация геометрии не должны менять магазины, предметы, патроны, HP, награды, ловушки и версию восстановления.

Когда будет разрешена общая сборка, ИИ снимает актуальный BuildReport: файлы `.data`, WASM, JS и их сжатые/распакованные размеры; сохранённые references и дубликаты. Затем нужен cold-cache и warm-cache тест одного и того же артефакта в Яндексе: transferred bytes, заголовки, download/decompress/compile, SDK-ready, scene-active, boat-ready, first-input. Не стирать сохранения ради cold-cache: использовать отдельный тестовый профиль.

Для плавности нужны median/p95/max frame time, количество длинных кадров, GC и Web heap на обычной остановке, большом городе и длинном маршруте; отдельно слабый телефон и desktop, кооп 4 и лобби 10. Heap после нескольких одинаковых циклов load/unload должен быть сопоставим при одинаковом активном составе. Счётчики Renderer не равны draw calls, Editor deltas не равны Web heap, средний FPS не описывает редкие зависания. Конкретные целевые пороги согласовать по полученной базе; принятых числовых бюджетов пока нет.

## Воспроизведение без Player Build

При закрытом другом экземпляре этого проекта вызвать установленный Unity Editor:

```powershell
& 'E:\Unity\Editors\6000.3.9f1\Editor\Unity.exe' -batchmode -nographics -quit -projectPath 'E:\GitFork\dead_boat' -executeMethod DeadBoat.EditorChecks.IncomingContentAudit.RunWebAudit -logFile 'E:\GitFork\dead_boat\Logs\WebOptimizationAudit20261113\Unity.log'
```

Пути заменить для другого компьютера; дождаться выхода процесса. Метод читает dependency/importer metadata и создаёт временные preview-клоны. Он не запускает игру, не сохраняет сцены/ассеты, не меняет настройки импорта. Для измерений нельзя одновременно использовать этот же проект в другом Unity. Сводка JSON в Docs — зафиксированный снимок этого прогона; повторный запуск пишет новые локальные отчёты в Logs, а не перезаписывает доказательства в Git.

Порядок работ в канбане:

1. **ИИ, DB-ON-125:** убрать создание заведомо задних городов, сохранив последовательность и восстановление; кэшировать bounds и разобрать authored root.
2. **ИИ, DB-ON-267:** облегчить игровые префабы/меши, затем точечно проверить импортеры без потери качества.
3. **ИИ, DB-ON-270:** убрать постоянные сканы EventSystem и неизменившиеся полные снимки; сохранить ввод и solo fallback.
4. **ИИ, DB-ON-268/269:** измерить/сократить boot-граф и добавить контролируемый отказ/повтор загрузки. Архитектуру bundles выбирать по фактическому выигрышу и совместимости.
5. **ИИ + владелец, DB-ON-002/027/028/036:** после разрешения на сборку сравнить payload, cold/warm старт и независимые устройства одним общим пакетом.

**Владелец** позднее принимает общий WebGL-пакет на целевых устройствах. Сейчас сборка и ручные действия не требуются. DB-ON-027/125 остаются открытыми; новые задачи267–270 только подготовлены к реализации, а не объявлены исправлениями игры.
