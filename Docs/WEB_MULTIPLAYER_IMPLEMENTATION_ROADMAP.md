# Что нужно для реализации WebGL мультиплеера

Статус: рабочая последовательность, 2026-09-25. Основа — [сценарий игрока](WEB_MULTIPLAYER_PLAYER_FLOW.md) и [проверка Fusion Shared](WEB_FUSION_SHARED_FEASIBILITY.md). Денежная стоимость разработки не учитывается.

Текущее приложение Photon `River` создано с лимитом **20 CCU** (по скриншоту Dashboard от 2026-09-25). Это достаточно для прототипа, но правило «пускать в онлайн до 100 человек» требует сменить тариф/тип приложения на доступный релизный лимит 100 CCU до запуска. На экране `Manage` не показаны SDK и его версия: перед импортом убедиться в списке приложений Photon, что `River` имеет тип **Fusion / Fusion 2**. App ID не публикуем в этом документе.

## Подготовка сервисов и доступов

| Что нужно | Для чего | Когда требуется |
|---|---|---|
| Photon Dashboard account и **Fusion 2 App ID** | Подключить Unity билд к Photon Cloud. Создать приложение типа Fusion / Fusion 2; App ID внести в `PhotonAppSettings`. На первом этапе достаточно development App ID. | Перед первым двухклиентным тестом. |
| Fusion 2.1 SDK | Shared Mode, NetworkRunner, сетевые объекты, свойства, RPC, сцены. В текущем `Packages/manifest.json` его нет. Актуальный официальный пакет на 2026-09-25 — 2.1.3; Photon требует входа в аккаунт для скачивания. | Перед сетевым срезом. |
| Тестовые WebGL сборки на каждой издательской площадке | Убедиться, что iframe/CSP разрешает Photon и Mirra, работает WebSocket, не рвётся сеть при рекламе и скрытии вкладки. | До переноса всех уровней. |
| Доступ к проекту Mirra Cloud, тестовые аккаунты и условия API | Проверить авторизацию, друзей, чат, фильтр и тариф. Установленный сейчас `MirraSDK 5` — SDK площадок/рекламы, **не** отдельный Mirra Cloud SDK. | До постоянных друзей и релизного чата. |
| Сервис проверки личности и правил комнат | Photon Custom Authentication должна связывать Photon user ID с проверенным ID аккаунта. Для строгого `friends only`, защиты от подмены и ценных наград может понадобиться небольшой доверенный backend; можно использовать сервис Mirra, если он подтвердит нужные server-to-server возможности. Секреты нельзя класть в WebGL билд. | После прототипа, до публичного релиза. |
| Тестовый режим рекламы каждого провайдера | Проверка открытия/закрытия, ошибок, возрождения и 1 секунды защиты после рекламы. | Перед сетевой реализацией рекламы. |

В `ProjectSettings/ProjectSettings.asset` уже стоит `runInBackground: 1`, что совпадает с рекомендацией Photon для WebGL sample. Это не гарантирует, что площадка или браузер не замедлят фоновую вкладку.

## Порядок реализации и результат каждого этапа

### 0. Защитить одиночный режим

- Ввести явный `OnlineMode`/feature flag и отдельный `OnlineBootstrap`: попытка подключиться, таймаут, доступная кнопка «Играть одному», лог причины отказа.
- Сохранить путь `LoadingScene → Lobby → уровень` без сетевых сервисов. Вход в онлайн-лобби не должен очищать незавершённый solo-save: сейчас `LobbyManager.Start()` записывает прогресс `-1`, это надо вынести из общего входа.
- Зафиксировать версии протокола и контента. Игроки с несовместимыми сборками не должны попадать в одну Session.
- **Готово, когда:** игра по-прежнему работает без интернета и при ошибке Photon.

### 1. Изолированный WebGL срез Fusion

- Импортировать Fusion 2.1 в отдельной ветке/checkout, настроить App ID и Shared Mode. Сначала отдельная минимальная сцена без текущих игровых систем.
- Два браузера в одной Session видят аватары, их движение и одну анимацию; один отключается и возвращается. Проверить на настоящей WebGL странице издателя, не только в Editor.
- Измерить FPS, память, RTT и трафик; закрыть/усыпить вкладку master и измерить время передачи роли.
- **Готово, когда:** подтверждено, что SDK работает на целевых origin, а не только на localhost.

### 2. Видимое лобби и друзья

- Сделать сетевое лобби как Shared Session с максимумом 10, персонажами и анимациями. Реализовать правило выбора старой/наименее заполненной комнаты, создание новой и повтор при гонке за последнее место.
- Настроить связь постоянного ID аккаунта с Photon ID, затем приглашение друга: в текущую комнату или совместный переход в другую/новую комнату.
- Подключить Mirra Friends и Chats только после проверки WebGL, server-side модерации прямой отправки и редактирования сообщений. Если проверка отрицательная — выбрать другой чат или серверный шлюз.
- **Готово, когда:** 11-й игрок создаёт вторую комнату; приглашённые друзья оказываются вместе; сообщения проходят обязательную проверку.

### 3. Отправление на корабле

- Добавить точку отправления и UI «Присоединиться / Создать». Параметры: уровень, желаемый размер 1–4, «Все / Только друзья».
- Ожидающий экипаж живёт в отдельной Shared Session с лимитом до 4; публичные отправления видны между лобби одного региона/версии, друзьям доступно приглашение по ID.
- При полном составе стартует общий сетевой таймер; лидер может нажать «Запустить сразу» при неполном составе. Состав фиксируется до загрузки уровня. Прежний участник после обрыва имеет отдельное окно возврата.
- Отработать уход лидера и смену master, отмену ожидания и возврат в лобби.
- **Готово, когда:** 1, 2, 3 и 4 человека доходят до одной сцены забега; случайный пятый не входит.

### 4. Сетевое ядро забега

- Разделить локального игрока и `RemoteAvatar`: `PlayerManager`, `PlayerInput`, `PlayerMovement`, `Inventory`, камера, UI и сохранения сейчас предполагают одного игрока через singleton. Удалённый персонаж не запускает локальные сервисы.
- Общий `RunState`: `runId`, уровень, seed, состав, фаза, абсолютная дистанция, поезд/топливо, победа/поражение. Объекты мира имеют стабильные ID. `BoardController` и `FixCoordinate` переходят на одну сетевую систему координат.
- Перевести геймплейные спавны, подбор, продажу, оружие, урон, врагов и боссов на запрос → проверка у authority → сетевое состояние. Статические декорации можно создавать из seed локально. Два запроса на один предмет дают одного победителя.
- Настроить snapshot для возврата, передачу master, поведение при выходе игрока и закрытие Session после ухода всех.
- **Готово, когда:** четыре браузера видят одинаковый поезд, предметы, врагов и результат босса после выхода master.

### 5. Животные, бонусы и реклама

- Отображать выбранных животных каждого игрока миниатюрными спутниками, которые повторяют историю движения игрока. Синхронизировать ID/стадию/порядок, не сетевую позицию каждого питомца каждый тик.
- Общие корабельные бонусы животных **всех участников складываются**: текущий `AnimalRunBuffs.Add` суммирует плоские прибавки и перемножает множители. Один authority вычисляет общий набор из состава на старте; личные бонусы остаются у своего игрока. Проверить баланс команды из 4.
- Вынести единый жизненный цикл рекламы для MirraSDK/YG/других провайдеров. Клиент запрашивает защиту у authority **до** открытия рекламы; затем блокируются действия игрока, на закрытии действует ещё 1 секунда защиты. Уход/ошибка/зависание снимают защиту по правилу времени.
- Возрождение по rewarded рекламе — личное событие игрока, подтверждаемое authority; остальные продолжают бой. `Time.timeScale = 0` в текущих провайдерах нельзя использовать как сетевую паузу забега.
- **Готово, когда:** реклама одного игрока не останавливает остальных, не убивает его во время показа и не даёт бесконечного бессмертия.

### 6. Выпуск и контроль расходов

- Проверить `MaxCcuReached` и другие причины отказа: новые игроки переходят в solo, уже собранная группа получает понятное сообщение при неудачном переходе в run. Держать запас подключений до фактического жёсткого лимита приложения: сейчас 20 CCU, для намеченного релиза нужно не меньше 100 CCU.
- Проверить вход/рекламу/фон вкладки/отключение сети на всех publisher origins; нагрузка не меньше 10 в лобби и 4 в забеге, затем несколько комнат одновременно.
- Измерить реальные KiB/s и месячный прогноз трафика, пиковый CCU, p95 кадра WebGL; выставить лимиты онлайн комнаты и мониторинг Photon.
- Результат забега и ценные награды не подтверждать только сообщением браузера master. До релиза определить server-side проверку или исключить недоверенные награды из сетевого режима.

## Что из этого мы можем начать без внешних доступов

В репозитории можно подготовить `OnlineBootstrap` и solo fallback, разделить локального/удалённого игрока, специфицировать `RunState`, провести инвентаризацию взаимодействий, спроектировать рекламу и сделать локальную тестовую сцену с заглушкой сетевого слоя. Для настоящего подключения двух браузеров нужен Fusion SDK и App ID. Для окончательного выбора Mirra как social/backend нужны доступ к проекту и проверяемые возможности API.
