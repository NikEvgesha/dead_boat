# Игровой сетевой рантайм: варианты для WebGL

Статус: архитектурное решение для обсуждения, 2026-09-25. Продолжение [основного плана](WEB_MULTIPLAYER_PLAN.md). Оценки ниже относятся к текущему проекту, а не к возможностям SDK «из коробки».

## Короткий ответ о Mirra Cloud

**Да, условно:** Mirra Cloud SDK документирует друзей, заявки, группы/кланы, чат и отдельную проверку текста. Их можно взять как основу социального слоя **после** проверки SDK в WebGL-билдах на издательских площадках, договора и серверной модерации. Его `GroupsService` описывает постоянные группы/кланы; временную группу из 1–4 друзей с лидером, готовностью и запуском забега придётся реализовать поверх доступного API либо в сервисе игрового рантайма. `ChatsService` использует WebSocket, но это события чата, а не передача координат, физики и состояния игрового мира.

В Mirra Cloud не найдено документированного готового Unity netcode для аватаров, поезда, AI, предметов и попаданий. Поэтому «всё остальное в Mirra» пока гипотеза для social/backend, а игровой рантайм выбирается отдельно. Даже при выборе Mirra как backend, сетевые комнаты на 10 человек и запуск отдельных забегов на 4 должны быть связаны с выбранным рантаймом через устойчивый ID аккаунта и ID сессии. `Chats.SendMessageAsync` и `ProfanityFilter.CheckAsync` — разные вызовы: необходимо получить подтверждение, что **сам сервер чата** проверяет текст при прямой отправке и редактировании сообщения.

## Что должен делать игровой рантайм

Рантайм — это не только «отобразить ещё три модели». Он решает следующие задачи:

1. **Соединение и комнаты.** Идентифицировать игрока, искать/создавать публичную комнату с настраиваемой ёмкостью (первое значение 10), не переполнять её при одновременном входе, переводить группу в отдельную сессию забега с максимумом 4 и возвращать в лобби. Сессии должны фильтроваться по версии сборки, региону и доступным местам. Лидер группы только нажимает «Старт» и выбирает уровень; право быть сетевым authority задаётся архитектурой, а не этой кнопкой.
2. **Игроки.** Для локального игрока использовать ввод и камеру; для остальных — только сетевой аватар. Передавать позицию, поворот, направление взгляда/оружия, компактное состояние анимации, выбранный предмет и экипировку. Удалённый аватар интерполирует движение и никогда не запускает местные сохранения, UI и ввод. Нужны spawn/despawn, имена и визуальное состояние для вошедших позже в лобби.
3. **Общий мир забега.** Назначить один источник истины для движения и топлива поезда, абсолютной дистанции, состояния предметов, геймплейных спавнов, AI, здоровья, урона и исхода забега. Передавать *намерение* игрока («подобрать item 123»), проверять расстояние/доступность и совершать переход состояния ровно один раз. Зафиксировать стабильные ID предметов и объектов, начальный seed и snapshot текущего мира для reconnect.
4. **Надёжность.** Восстановление соединения по `runId` в коротком окне, выход лидера/водителя/authority, повторные сообщения, смена вкладки, падение браузера, несовпадение версий. До запуска кооператива разрешать переход в solo при ошибке подключения; после начала общего забега нужен reconnect либо честное завершение сессии, а не тихий переход каждого в личный мир.
5. **Безопасность и результаты.** Не доверять сообщениям клиента о добыче, валюте и завершении уровня. Для ценных постоянных наград нужен отдельный доверенный механизм проверки или серверный authority. Социальный ID Mirra и сетевой ID сессии связывать через проверяемый токен, а не переданный клиентом никнейм.
6. **WebGL-производительность.** Передавать часто только изменяющееся состояние, а дискретные действия — событиями; применять интерполяцию, ограничение частоты, области интереса и бюджет AI/спавнов. Стартовый ориентир для проверки — 10–20 обновлений поз/с у близких игроков; конечные параметры выбрать по p95 кадра, RTT, трафику и потерям на четырёх реальных браузерах и площадках. HTTPS-страницам необходим WSS; вкладка в фоне может замедляться или останавливаться.

### Что особенно требует переделки в этой игре

`PlayerManager`, `PlayerInput`, `PlayerMovement`, `Inventory` и UI предполагают одного игрока через singleton: отделить `LocalPlayerContext` от сетевого `RemoteAvatar`. `BoardController` должен иметь единого владельца поезда. `LocationSpawner`/`LocationContentSpawner`/`ZombieSpawner` не могут независимо вызывать локальный `Random` и создавать геймплейные объекты: authority назначает spawn ID и состояние. `ZombieController`/боссы должны видеть до четырёх целей. `PickableItem` должен выдавать предмет только после подтверждения владельца мира. `FixCoordinate` должен хранить абсолютные сетевые координаты, а локальный сдвиг сцены применять лишь как представление. `SaveManager` разделяет личный solo-save, общий checkpoint и награды участников.

## Вариант A: Photon Fusion 2 Shared Mode + Mirra Cloud

**Схема.** Браузеры подключаются к Photon Cloud. Каждый владеет своим аватаром; один выбранный master client ведёт поезд, AI, геймплейные спавны и предметы. Photon доставляет и хранит сетевые свойства комнаты. Mirra Cloud отвечает за социальный слой при выполнении проверок выше.

**Плюсы:** официально рекомендуемый Photon режим для WebGL; готовые комнаты, state replication, RPC и смена master client; не нужно разворачивать Unity сервер для каждой игры; быстрый путь к видимым аватарам и первому кооперативному прототипу.

**Минусы:** общий мир всё равно исполняется на браузере игрока. При фоне/выходе master client требуется перенос authority и продолжение AI/поезда; до переноса возможна пауза. Доверять такому клиенту результаты и покупки нельзя. Логика общего мира концентрируется у master client, поэтому «Shared» не делает произвольное изменение объекта каждым клиентом безопасным. Photon тарифицирует CCU/трафик; Mirra — отдельный договор. Социальный ID и Photon user ID надо связать.

**Когда выбирать:** если первичны быстрый WebGL-релиз и ограниченный бюджет серверной эксплуатации; постоянные ценные награды из забегов либо отключаются на первом этапе, либо подтверждаются отдельным backend.

## Вариант B: Mirror + выделенный Unity сервер + Mirra Cloud

**Схема.** WebGL клиенты Mirror используют WebSocket/WSS. Linux headless сборка Unity на нашем хостинге авторитетно исполняет поезд, AI, предметы и урон; сервер рассылает snapshots и события. Перед ним reverse proxy/TLS; отдельный диспетчер выделяет сессии и следит за загрузкой. Mirra Cloud остаётся social/backend. Mirror поставляет сетевую библиотеку и транспорт, **не серверы в облаке**.

**Плюсы:** лучший контроль целостности общего мира, проверок подбора и наград; закрытие вкладки любого игрока не останавливает симуляцию остальных; можно менять правила, лимиты, логирование и размещение регионов без привязки к Photon Cloud. Хороший конечный вариант, если кооператив станет главным режимом.

**Минусы:** собственные build/deploy, WSS, мониторинг, защита и оплата работающих процессов. Публичное лобби на 10 и отдельные забеги на 4 требуют управления множеством сессий; стандартный `NetworkRoomManager` — комната перед переходом в игровую сцену, а не готовый глобальный сервис для тысяч параллельных комнат. Потребуется свой room allocator/matchmaker и план плотности сессий на процесс. WebSocket поверх TCP может добавлять задержку при потерях; замерять на реальных сетях. Объём интеграции и DevOps выше.

**Когда выбирать:** если важны доверенные награды, стабильное продолжение забега после ухода любого игрока и есть бюджет на постоянную эксплуатацию сервера. Один серверный процесс на забег — простая исходная модель; оптимизацию числа сессий на процесс решать после профилирования, не закладывать как бесплатную возможность Mirror.

## Вариант C: Unity NGO + Multiplayer Services/Relay + Mirra Cloud

**Схема.** В WebGL используется Unity Transport через WSS и Unity Relay; NGO синхронизирует объекты. В дешёвой схеме один браузер играет роль host; Unity предоставляет соединение через Relay, но не исполняет за него симуляцию. В варианте dedicated Unity сервер размещается отдельно, и по свойствам эксплуатации он близок к варианту B.

**Плюсы:** официальный Unity стек, готовые NGO примитивы и Relay без самостоятельной настройки публичных адресов игроков; можно сохранить Mirra social/backend. При выделенном сервере возможна авторитетная симуляция.

**Минусы:** browser-host крайне уязвим к закрытию/усыплению вкладки. Выбор нового host в сервисе не равен восстановлению живого состояния поезда, врагов и предметов: snapshot и перенос надо реализовать самим. На выделенном сервере повторяются расходы и DevOps варианта B. Совместимость конкретных версий Unity 6/NGO/Transport/MPS и всех издательских iframe требует прототипа. Сочетание Mirra и Unity сервисов добавляет две системы identity/сессий.

**Когда выбирать:** если команда предпочитает официальный Unity SDK или уже использует его. Для этой игры NGO + browser-host не выглядит надёжным вариантом релизного забега; вариант с dedicated нужно сравнивать с Mirror на небольшом вертикальном срезе.

## Вариант D: собственный WebSocket рантайм / Nakama + Mirra Cloud

**Схема.** Пишем протокол сообщений и синхронизацию Unity сами; сервер может быть собственным приложением или на Nakama. Nakama помогает с matchmaker/комнатами и server-authoritative логикой, но синхронизацию Unity компонентов, физики и существующих скриптов не выдаёт автоматически.

**Плюсы:** максимальный контроль над трафиком, размером сообщений и backend-правилами; можно оптимизировать именно поезд, предметы и 4 аватара; Nakama закрывает часть серверных задач.

**Минусы:** самый большой объём инженерной работы и тестирования (протокол, snapshot, интерполяция, reconnect, версии, отладка). Переписать Unity AI/физику в серверной логике вне Unity может оказаться дороже выделенного Unity сервера. При Mirra + Nakama появляется два backend-провайдера с пересекающимися аккаунтами/чатом. Оправдано только после измеренного ограничения готовых решений или если команда уже сильна в этом стеке.

## Сравнение для принятия решения

| Критерий | Fusion Shared | Mirror dedicated | NGO + Relay browser-host | Свой WS/Nakama |
|---|---|---|---|---|
| WebGL | Официально рекомендован | Да, WSS | Да, WSS | Да, WSS |
| Источник истины забега | Браузер master client | Наш Unity сервер | Браузер host | Наш сервер, если сделаем |
| Сервер игры от поставщика | Photon Cloud распределяет состояние, не запускает AI | Нет | Relay передаёт пакеты, не запускает AI | Нет; Nakama даёт серверную платформу |
| Уход владельца мира | Перенос master и восстановление логики | Забег продолжается | Нужен перенос host **и** состояния | Реализуем по своему протоколу |
| Проверяемые награды | Отдельный доверенный backend | Возможны на сервере игры | Отдельный backend | Возможны на своём сервере |
| Первоначальная разработка | Средняя | Высокая | Средняя, но высокий риск отказов host | Очень высокая |
| Эксплуатационные расходы | Photon CCU/трафик + Mirra | VM/контейнеры, трафик, мониторинг + Mirra | Unity Relay + Mirra; dedicated оплачивается отдельно | Серверы/Nakama + Mirra |

Это относительная оценка, не коммерческая смета. Для денег нужны пик CCU, средняя длительность сеанса, профиль трафика, регионы, условия Mirra и тестовая плотность Unity серверов. Численные тарифы и общий план приведены в [основном документе](WEB_MULTIPLAYER_PLAN.md).

## Рекомендация и первый эксперимент

Рекомендую **A для вертикального среза**: Fusion Shared + Mirra social, с заранее выделенным интерфейсом `RunAuthority`, чтобы общую логику не зашить в Photon компоненты. За 1 эксперимент должны работать две настоящие WebGL вкладки на целевой площадке: вход в одну комнату, два аватара с анимацией, один предмет с конкурентным подбором, общий поезд, один враг, выход master client и продолжение забега. Затем нагрузка с четырьмя вкладками и измерение трафика/кадра. Если перенос master, сохранность мира или доверенные награды не проходят требования релиза, переходить на **B: Mirror + dedicated Unity server**. Перенос рантайма всё равно затронет сетевые адаптеры и потребует работы; интерфейс `RunAuthority` лишь уменьшит зависимость правил игры от конкретного SDK.

Для Mirra отдельный контрольный эксперимент: авторизация и друзья в каждом WebGL origin; общий чат на 10; отправка и редактирование сообщения прямым вызовом API в обход клиентской проверки; блокировка; создание/очистка каналов; связь Mirra account ID с Photon/Mirror сессией. Если серверная фильтрация прямой отправки не подтверждается, понадобится свой серверный шлюз чата либо иной сервис модерации.
