# Совместный запуск, сид и физика

Дата: 2026-09-30. Текущий этап — прототип совместной загрузки, не готовый кооперативный игровой цикл.

## Что реализовано

`SharedDepartureState` создаётся один раз создателем экипажа. В сетевом состоянии находятся seed, версия генерации, уровень, целевой состав, TickTimer и итоговый roster. Это MasterClientObject без уничтожения при уходе authority: состояние должно переходить следующему Shared master. Проверка переноса владельца на двух клиентах ещё требуется.

Полный состав запускает 5 секунд отсчёта; текущий Shared master может нажать «Запустить сейчас». Изменение состава отменяет отсчёт; если новый состав снова полный, начинается новый отсчёт. На старте комната закрывается и скрывается, фактические PlayerRef фиксируются. Клиент, которого нет в roster, не загружает забег. Лидер после ухода предыдущего — новый Shared master.

При одном участнике Runner выключается и запускается обычный одиночный уровень. При 2–4 участниках Runner, состояние отправления и аватары переживают загрузку. Каждый клиент открывает выбранный уровень через существующий LoadingManager/GameLoader, получив Phase=2. Второго подключения Photon нет. Пока сцены не содержат зарегистрированных Fusion scene objects, используется этот протокол поверх обычной Unity-загрузки. Перед добавлением сетевых объектов, размещённых прямо в сценах, необходим настоящий INetworkSceneManager с регистрацией scene objects; нынешний LobbySceneManager этого не умеет.

В прототипе действует `SharedRunPreviewSave`: вызовы SaveManager для прогресса/наград идут в память и не перезаписывают solo-save; настройки звука/чувствительности сохраняются обычно. При индивидуальном EndGame сначала завершается локальный Runner, затем восстанавливается обычный провайдер и открывается лобби. Это временная изоляция теста, не реализация сохранения совместного забега. Сервисы, обращающиеся к хранилищу напрямую в обход SaveManager, эта обёртка не покрывает.

Новая версия использует каталог `river-departures-v2`, чтобы старый WebGL-клиент не оказался в комнате с неизвестным сетевым префабом.

## Генерация

`RunRandom` v1 — xorshift32 с явным стабильным хешем имени потока; GetHashCode/System.Random/Unity Random.InitState не используются. Поток создаётся по `(seed, имя, индекс)`. Чужие вызовы, эффекты и разная частота кадров не сдвигают его.

| Система | Ключ / решение | Текущее состояние |
| --- | --- | --- |
| Расстояния и выбор локаций | `layout`, последовательный индекс локации; локальная копия пула без повторов | Перенесено в прототип |
| Начальные предметы | `items:procedural:N` или стабильный путь scene-локации | Перенесено; личные модификаторы шанса временно исключены из общего мира |
| Начальные враги | Отдельный `enemies:…`, собственный shuffle и выбор префаба | Перенесено; дальнейший AI не синхронизирован |
| Первый гарантированный egg | Только procedural:0 | Общая базовая генерация; дальнейшие изменения шанса по собранным яйцам должны задаваться authority |
| Декорации | Стабильный сегмент маршрута + индекс | Ещё локальный Random; сейчас зависит от позиции игрока, требует переделки |
| Ассортимент ItemStore | Stable store ID + номер обновления | Ещё локальный Random; общий ассортимент должен фиксироваться authority |
| Ночные спавны ZombySpawners | Authority публикует spawn ID/тип/позицию/уровень | Ещё локальная логика |
| Выбор атаки боссов | Authority выбирает и публикует атаку + tick старта | Ещё локальная логика |
| Разброс выстрела / случайный урон | Идентификатор атаки + результат authority | Не воспроизводить из общего изменяемого Random |
| Карточки улучшений | Персональный поток по игроку и номеру выбора; подтверждённый выбор в состоянии игрока | Отдельная работа; параметры лодки агрегируются по принятому правилу |
| Шаги, звук, всплывающие цифры, loading art | Локальный Random | Допустимо: не влияет на мир |

Предметы/враги получают `WorldSpawnIdentity` вида `procedural:N:item:P` и `procedural:N:enemy:P`. Это ключ генерации, не Fusion NetworkId. Порядок точек/префабов и баланс входят в версию контента; менять их без новой совместимой версии нельзя.

Начальный мир можно построить повторно по ключам. После действий игроков одного seed недостаточно: собранные предметы, топливо, положение лодки, здоровье и выбранные карточки должны приходить из снимка. В текущем прототипе такого reconnect ещё нет.

## Физика: выбранная схема для первого рабочего кооператива

Рекомендация для нашего WebGL-прототипа: свободные предметы считает один authority; прокси кинематические, положение интерполируется. Это решение проекта с ограничением взаимодействий через запросы. У Fusion 2.1 есть также Forecast для непосредственных физических взаимодействий всех клиентов. [Официальное сравнение подходов](https://doc.photonengine.com/fusion/v2/manual/physics/physics-overview).

| Объект | Кто считает | Что передаём | Как выглядит на других клиентах |
| --- | --- | --- | --- |
| Игрок | Его клиент | Поза, движение, выбранный предмет, действия | Уже существующий аватар; коллизии не должны управлять чужой лодкой |
| Лодка | Shared coordinator, водитель посылает команды | Водитель, скорость, маршрутная дистанция, топливо, итоговые параметры | Локальное плавное движение одной общей лодки; пассажиры в координатах лодки |
| Свободный физический предмет | Coordinator | Stable ID, поза, velocity/angularVelocity, sleep, состояние, revision | Kinematic proxy; запросы на бросок/толчок проверяет authority |
| Предмет в руке/инвентаре | Подбор подтверждает coordinator | Владелец, слот, item ID | Визуал на hand socket, без свободной Rigidbody-симуляции |
| Предмет прикреплён к лодке | Coordinator | Parent ID, локальная поза, режим attached | Child/proxy; физика выключена |
| Статичная локация | Общая генерация | Seed/version + ключи, изменения состояния | Нет постоянных transform-пакетов |
| Враги и боссы | Coordinator | Поза, HP, состояние атаки, подтверждённый урон | Интерполяция и анимации; локальный AI выключен |
| Животные-спутники | Владелец/общий подтверждённый состав | Тип, порядок в цепочке, следование | Декоративное следование; без сетевых столкновений каждого животного |

### Подбор и смена режима предмета

`RequestPickup(stableId, expectedRevision, requestId)` → authority проверяет расстояние, наличие, вместимость и уже выданное владение → меняет общее состояние → все скрывают предмет мира, победитель получает его в инвентарь. RequestId обеспечивает идемпотентность, revision исключает двойной подбор. RPC сообщает просьбу; долговечный результат находится в Networked state, чтобы новый клиент увидел его без проигрывания старого RPC.

Режимы: World/Sleeping → Held/Inventory → Attached → World. При смене режима атомарно меняются владелец, parent, поза и revision. Нельзя одновременно оставлять предмет в мире и в чужом инвентаре.

### Изменения существующего кода

- PickableItem.Update переключает `isKinematic` по расстоянию до локального игрока. Для сетевых предметов это разрешается только authority; прокси не выполняют данный участок.
- BoardController.FixedUpdate сейчас использует локальный PlayerInput и локальные бонусы. Нужны сетевое место водителя, подтверждённый input и общие параметры лодки: лучший бонус профессий/животных отдельно по параметру, сумма карточек участников.
- LocationSpawner загружает локации по локальной позиции. Геометрия теперь повторима, но общий список активных сегментов должен определяться дистанцией лодки/координатором, чтобы один игрок не удалил нужный другому остров.
- FixCoordinate переносит корни сцены и записывает разные PlayerAddPos/BoardAddPos. По сети передаются логические координаты (`local + origin`) или координаты относительно лодки; локальный перенос origin не является игровым движением. Сначала нужен тест двух клиентов по разные стороны порога rebasing.
- Физические удары игроков о Rigidbody и игрок об игрока для первого этапа ограничиваем. Непосредственное двустороннее толкание добавляется отдельно после измерения Forecast.
- Pause/реклама останавливает ввод конкретного игрока, но не сетевую симуляцию всей группы; invulnerability имеет подтверждённый срок + 1 секунду после рекламы.

### Варианты и компромиссы

1. **Authority + kinematic proxies (первый этап):** меньше CPU, простая миграция состояния, понятный победитель подбора. Минус — задержка подтверждения броска/толчка, нельзя ожидать честного локального столкновения двух чужих Rigidbody.
2. **Fusion Forecast:** плавнее прямое физическое взаимодействие. Минусы — физика на каждом клиенте, коррекции, дороже на слабом WebGL; не гарантирует идентичную физику по seed. Испытывать на одном типе предмета, не включать сразу всему миру.
3. **Упростить механику:** фиксированные места на лодке, прикреплённые объекты, предметы в руке без Rigidbody. Дешевле и стабильнее, но меняет свободу игрока. Не заменять существующие механики без отдельного решения владельца.
4. **Авторитетный сервер:** лучше контроль урона/экономики, но отдельная серверная инфраструктура и другой runtime; выходит за принятую Fusion Shared архитектуру.

## Восстановление и миграция (ещё не реализовано)

Snapshot: session/content/generator version, seed, roster со стабильными player IDs, revision/tick, активные сегменты, поза/топливо/водитель лодки, состояние каждого предмета, HP/фазы врагов, инвентари, улучшения и состояние победы. У важных действий request ID и возрастающая revision; новый authority продолжает её, не выдаёт награду повторно. Сначала snapshot, затем более новые подтверждённые события; частые позы передаются обычными сетевыми snapshots, их не нужно записывать в бесконечный event log.

Возвращающийся клиент генерирует нужные сегменты и накладывает snapshot. При отсутствии живого состояния нельзя делать вид, что seed восстановил забег. Восстановление после закрытия последней вкладки потребует отдельного сохранения на backend.

## Проверки и порядок

Проверено в Unity Editor: компиляция; независимые потоки и восстановление ключа на пяти seed; две независимые копии четырёх реальных LocationSpawnCollection × 200 локаций дают одинаковые расстояния и префабы. Это проверка генерации, не две сетевые вкладки.

Следом:

1. **ИИ:** проверить транспорт на двух WebGL-клиентах: тот же session/seed/version, общий таймер, одинаковый уровень, видимость аватаров, выход одного, сохранность solo-save. До этого прототип не принят.
2. **ИИ:** одна общая лодка, водитель, fuel и логические координаты; готовность клиентов перед началом симуляции.
3. **ИИ:** один тип физического предмета + атомарный подбор + бросок/attachment; после проверки распространять на каталог.
4. **ИИ:** authority врагов, урон, победа, reconnect snapshot; затем разрешать постоянные награды.
5. **Владелец:** ручная приёмка на двух устройствах в черновике Яндекс, включая задержку/перезаход/выход лидера. Текст и оформление UI — отдельная итерация.
