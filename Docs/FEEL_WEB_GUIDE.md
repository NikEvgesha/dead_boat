# FEEL в Dead Boat: правила использования

Изучено 06.11.2026. Установлен FEEL **5.9.1** (`Assets/Feel/readme.txt`); Unity остаётся **6000.3.9f1**, обновление движка отменено владельцем. MCP обновлён владельцем до1.7.0 и отвечает на запросы. Текущий GraphicsSettings указывает Built-in pipeline; в manifest нет Cinemachine/URP/HDRP. Применяется существующий uGUI, включая `UnityEngine.UI.Text`.

Первый прототип интеграции карточек реализован в DB-ON-128; остальные эффекты ниже остаются планом. SDK/FEEL не изменяем. Современная онлайн-документация описывает FEEL6.3; точные поля и методы сверяем с локальным5.9.1.

## Как работать с установленным API

Базовая единица — `MoreMountains.Feedbacks.MMF_Player`: последовательность `MMF_Feedback`, запускаемая кодом или UnityEvent. Поддерживает явные `Initialization()`, `PlayFeedbacks()`, `StopFeedbacks()`, `RestoreInitialValues()`, а также `AddFeedback(MMF_Feedback)`. Назначать ссылки/параметры до Initialization; повторять инициализацию при смене кэшируемых целей, а не на каждом кадре.

Поля5.9.1, важные для нас:

| Настройка | Применение |
|---|---|
| `InitializationMode = Script` | Программно собранные последовательности, после назначения целей |
| `PlayerTimescaleMode = Unscaled` | Часы самой последовательности UI, включая cooldown |
| `ForceTimescaleMode = true`, `ForcedTimescaleMode = Unscaled` | Часы индивидуальных UI-эффектов при паузе |
| `CanPlayWhileAlreadyPlaying = false` + `CooldownDuration` | Защита от наложения и спама |
| `StopFeedbacksOnDisable`, `RestoreInitialValuesOnDisable` | Остановка/сброс; учитывать самостоятельное отключение компонента после завершения |
| `OnlyPlayIfWithinRange`, `RangeDistance` | Ограничение дальних пространственных эффектов |
| `PerformanceMode` | Оптимизация **инспектора**, не WebGL-runtime |

Проверенные по исходникам компоненты: `MMF_Scale` (Transform, в том числе RectTransform), `MMF_Position`, `MMF_Graphic` (uGUI Graphic: Image и Text), `MMF_Image`, `MMF_ImageAlpha`, `MMF_ImageFill`, `MMF_CanvasGroup`, `MMF_AudioSource`, `MMF_Particles`, `MMF_ParticlesInstantiation`. У последнего режимы Cached/OnDemand/Pool, штатный Mode=Pool, ObjectPoolSize=5, MutualizePools=false. Для частых эффектов заранее выбирать малый ограниченный пул/готовую систему; не считать наличие режима Pool доказательством подходящего бюджета.

**Проверенная особенность5.9.1:** Update у MMF_Player сам выставляет `enabled=false` после завершения, вызывая OnDisable. При `RestoreInitialValuesOnDisable=true` окончательный scale/alpha поэтому откатывается и без закрытия GameObject. Первый стенд ожидал сохранения destination1.2 при таком флаге и получил1.0; источник подтверждён кодом Update/OnDisable. Повтор с флагомfalse завершился в1.2 при timeScale0. Для entrance/fade, чей результат должен остаться, оставлять флагfalse и вызывать StopFeedbacks/RestoreInitialValues явно в адаптере при закрытии/переиспользовании. Для короткого punch, который должен завершаться в исходном состоянии, возврат допустим. Не назначать одну политику всем последовательностям.

## Что применяем первым

1. **Карточки:** короткое последовательное появление, небольшой отклик выделения/нажатия, цвет рамки редкости, подтверждение принятой награды. Работает только на визуальном дочернем объекте; контейнер разметки и существующий Animator панели не получают конкурирующие анимации. На мобильном hover отсутствует — обязателен press/select-отклик. Эффект не блокирует ввод и не меняет текст/числа локализации.
2. **Предметы и награды:** краткий отклик иконки/счётчика после подтверждённого подбора, покупки или награды; объединять поток частых событий.
3. **Боевые карты:** ясный локальный сигнал третьего удара/лечения/низкогоHP, без постоянных вспышек на каждом кадре. Лечение показывать после подтверждения фактически снятогоHP, а не по отправке RPC.
4. **Остальной бой:** аккуратный hit-marker, короткая реакция локальной камеры и ограниченные частицы. Удалённый игрок не трясёт камеру наблюдателя. Сила движения должна иметь возможность уменьшения/отключения при дальнейшем UI настроек.

Это последовательность будущей работы, не обещание включить все эффекты одновременно. Первая задача — DB-ON-128, карточки.

## Границы интеграции

- FEEL воспроизводит подтверждённые игровые события локально. Не синхронизируем покадровые кривые/частицы по Photon и не добавляем RPC для каждого кадра эффекта. FEEL не выдаёт карты, деньги, урон, лечение или предметы: повтор/отмена анимации не повторяет игровую операцию.
- Не анимировать сетевые корни, Rigidbody/коллайдеры, реальные точки лодки/крепления предметов. Для эффекта использовать визуального ребёнка, не влияющего на авторитетное положение.
- В меню применять unscaled-время; во время рекламы отдельно останавливать/приглушать необязательные эффекты и звук. Один unscaled-режим не обеспечивает такую остановку.
- Не подключать `MMTimeManager`/`MMF_TimescaleModifier` для hit-stop: у нас уже есть PauseManager, реклама, восстановление и независимая Shared-симуляция. Демо slow-motion может конфликтовать с ними.
- Не заменять наш загрузчик/барьер Photon на MMSceneLoading, сохранения на MMTools Saving, управление звуком на новый глобальный менеджер. Использовать существующие настройки громкости/рекламы. NiceVibrations с нативными iOS/Android-вызовами не является гарантированной вибрацией браузера.
- Вариативность VFX может быть локальной; её случайность не должна менять общий сид мира/магазина или результат боя. Если эффект потребляет UnityEngine.Random, отделять/сохранять его состояние при работе рядом с чувствительной к случайности генерацией.

## Веб-бюджет и импорт

Первый вариант для карточек: scale/alpha/color/короткий звук, без дополнительных камер, RenderTexture, blur, bloom, полноэкранного distortion, шейдерного glow или бесконечных частиц. Цветная рамка/готовый лёгкий спрайт предпочтительны как начальный вариант редкости. Это инженерная рекомендация, не измеренный сравнительный benchmark.

Не устанавливать зависимости демо ради UI. HDRP/URP-демо и `FeelDemosURP.unitypackage` не конвертируют нашу игру автоматически. Не добавлять демосцены в Build Settings, demo-prefab/материалы в игровые ссылки или большие эффекты в Resources. Ничего из импортированного не удалялось.

Локальная инвентаризация вместе с meta: FeelDemos162.7MiB, HDRP27.4MiB, URP35.0MiB, MMFeedbacks61.1MiB, MMTools72.5MiB, NiceVibrations55.0MiB; всего приблизительно414MiB. Это **диск проекта**, не WebGL-загрузка. В пакете есть небольшие Resources-ассеты, включая профили постобработки и вспомогательные prefab: нельзя обещать, что весь неиспользуемый импорт будет исключён. Настоящий вклад устанавливается по Build Report и сжатым data/wasm после отдельно разрешённой сборки; сейчас сборка не выполняется.

При интеграции измерять: простой UI, открытие/повторные выборы карт, частые награды, активный бой четырёх игроков. Сравнить CPU/GC, UI rebuild/batches, GPU/overdraw и память; отдельно слабый мобильный браузер и вкладка после рекламы/возврата. Число эффектов и частиц ограничивается на клиенте, дальние/невидимые не запускаются. Целевой предел миллисекунд назначить после базового измерения, не выдумывать FPS-гарантию по одному Editor-тесту.

## Проверки и источники

Unity на установленной версии разрешает тип MMF_Player, компиляция завершена, Play Mode до проверки выключен. Это не WebGL-валидация.

В изолированной RecoveryProtocolProbe выполнен настоящий MMF_Player+MMF_Scale: unscaled ToDestination1→1.2 завершился при timeScale0, явный restore вернул1, отключение во время второго play остановило player и вернуло исходный scale — PASS. Эффекты в игровые сцены не добавлены. Тест проверяет базовую механику, а не FPS/GC/размер/работу браузера. Лог: `Logs/FEEL-Study-20261106.log`.

После остановки Play: VerifyRestored PASS для сохранённых owner keys и стартовой сцены; временных MMF_Player0, NetworkRunner0, Playfalse.

Основные локальные источники: `Assets/Feel/readme.txt`, `MMFeedbacks/MMFeedbacks/Core/MMF_Player/MMF_Player.cs`, `Core/Legacy/MMFeedbacks.cs`, `Core/MMFeedbackTiming.cs`, исходники соответствующих feedbacks и `NiceVibrations/Scripts/Components/LofeltHaptics.cs`.

Документация автора (версию учитывать): [MMF Player](https://feel-docs.moremountains.com/mmf-player.html), [основные понятия и время](https://feel-docs.moremountains.com/core-concepts), [перечень feedbacks](https://feel-docs.moremountains.com/list_mmfeedbacks.html).


## Подключение карточек — DB-ON-128

CardFeelFeedback создаётся LevelUpButtomUI один раз: анимирует существующий Point/LevelUpElement, к которому не привязаны кривые Animator. Иерархия Point/Choise и Button не меняется. Два MMF_Player на карту: вход0.2с (scale0.94→1.018→1 и alpha0.72→1), нажатие0.14с (scale1→0.965→1) и alpha рамки. Рамка — четыре UI Image без текстуры/материала/частиц, цвет по редкости. PointerDown поддерживает touch; select/hover добавляют умеренное выделение. Рекламная защита возвращает нейтральный вид и запрещает проигрывание позади рекламы.

CardChoiceFeedback — один переиспользуемый значок подтверждённой награды вне закрываемой панели; исчезает за0.48с и прекращает Update. Нет нового AudioSource: используется SoundManager.PlayUIClick с текущим mixer/настройками. Всего7 MMF_Player для трёх карточек, никаких новых камер/RenderTexture/сетевых сообщений. Инициализация/Play сохраняют UnityEngine.Random.state, поэтому визуал не должен менять выдачу карт/генерацию.

Выдача происходит в обычном игровом callback сразу после результата рекламы; прежняя искусственная задержка0.2с удалена. FEEL ничего не выдаёт. Версия предложения и флаг завершения отвергают старый/повторный callback. Следующее предложение не принимает выбор в первые0.25с после награды: это debounce от двойного клика, независимо от длительности FEEL. Реролл во время занятого выбора не списывает валюту. Проверки: Assets/Online/Editor/CardFeelProbe.cs. Все изменения создаются на runtime-объектах; исходные FEEL, prefab и Animator не переписываются.


## Боевой HUD карточек — DB-ON-129

CombatCardHud использует ту же фабрику лёгких MMF_Player и scale-pulse на3.5% для трёх локальных строк. Обновление данных10Hz, текст перестраивается по изменению ранга/состояния/суммы/языка; в неподвижном состоянии нет новых строк на каждом кадре. Нет подписки игрового кода на FEEL-events. Лечение агрегируется0.3с; усиленный удар отображается после существующего подтверждения урона. Новые сетевые поля/сообщения не требуются.

HUD создаётся один раз на LevelUpUi, использует его Canvas и текущий UI-font, иконки существующих карточек. Неполученные карты и социальное лобби скрыты; после паузы/рекламы не проигрывать старые pulses. На мобильных устройствах расположение/шрифт требуют общей владельческой приёмки; FPS этим шагом не гарантируется.

## DB-ON-131: готовность стрелковых карт

HUD расширен максимум до5строк/5переиспользуемых MMF_Player: Верная рука и Новый заход дают мягкий pulse при переходе в ready, без отдельного Canvas, сетевых событий или игрового действия из FEEL. Poll10Гц, текст только при изменении, не перестраивать эффекты на каждом выстреле. Скрытие/исчезновение после расходования проверяет CombatCardHudProbe. UI-бюджет в слабом WebGL всё ещё требует общего браузерного теста; Editor не доказывает FPS.
