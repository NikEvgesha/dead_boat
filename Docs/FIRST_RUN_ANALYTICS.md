# Воронка обучения — DB-ON-049

События создаёт FirstRunAnalytics, отдельная часть игрового кода. MirraSDK и Mirra Cloud SDK не изменены. Автоматические SessionsStarted/Playtime SDK не вызываем повторно.

## Получатель и настройка

В установленной MirraSDK5 конфигурация MirraWebConfiguration выбирает FallbackEventsReporter: `Report` пользовательского события там только пишет предупреждение. Поэтому воронка использует **Mirra Cloud AnalyticsService.SendBatchAsync**, существующий MirraSocialService и его гостевую сессию. Это не подключение к Photon и не блокирует обучение при отсутствии интернета. Платформа/ветка берутся из существующей Cloud Configuration.

**Перед приёмкой в вебе ИИ или владелец должен зарегистрировать в Analytics проекта Dead Boat на нужной ветке/платформе следующие event keys и разрешённые параметры.** Наличие определений на сервере в этом этапе не проверено, они не создавались. Имя можно переводить в консоли, ключи должны остаться точными:

| Ключ | Смысл |
|---|---|
| first_run_enter | Новая попытка, до загрузки учебной сцены |
| first_run_resume | Запуск с существующей незавершённой попыткой |
| first_run_step_started | Первое начало конкретного этапа |
| first_run_step_completed | Завершение этапа, один раз на попытку |
| first_run_step_resumed | Восстановлен текущий этап, без нового завершения |
| first_run_death | Смерть; повторные вызовы до возрождения подавляются |
| first_run_revived | Возрождение после смерти |
| first_run_retry | Перезапуск урока; затем новый attempt_id и enter |
| first_run_skipped | Явный выход в лобби |
| first_run_completed | Победа в учебном забеге |
| first_run_lobby_enter | Лобби действительно загружено после выхода/финала |

Для всех событий разрешить **строковые** параметры: `event_id`, `attempt_id`, `step`, `reason`, `platform`, `content_version`, `seed`, `sequence`, `active_seconds`, `occurred_at_utc`. SDK batch передаёт словарь string/string. `Date` — UTC события, не время повторной доставки. Числовые строки разбирать в отчёте как числа.

`attempt_id` — случайный GUID, живёт через refresh, меняется при повторе урока. Не содержит ника, платформенного player ID, токена или идентификатора устройства. Cloud автоматически применяет свою авторизацию запроса; анонимность полей не означает, что Cloud не связывает запрос со своей сессией. `event_id=attempt_id:sequence` нужен для удаления дублей при повторной доставке.

Этапы в порядке прохождения: `pickup`, `sell`, `collect_money`, `buy_fuel`, `pickup_purchase`, `refuel`, `steer`, `sail_first`, `first_fight`, `egg`, `first_card`, `sail_second`, `supplies`, `second_fight`, `second_card`, `sail_boss`, `boss`. Отдельное значение `loading` позволяет увидеть потери до готовности сцены. `active_seconds` — накопленное время готового урока в фокусе, включая раздумья в карточном/паузном меню; без загрузки, фона и экрана смерти. Разница значений на start/complete даёт длительность этапа; между refresh пауза не прибавляется.

## Доставка и ограничения

Состояние воронки и очередь хранятся вместе с отдельным учебным профилем. Событие записывается до отправки. По 8 событий в запросе, не более одного запроса одновременно, повтор не чаще30с. При завершении/выходе очередь сохраняется и продолжает отправляться в лобби или после следующего входа. Верхняя граница128 событий: при длительной недоступности старые вытесняются, счётчик `telemetry.dropped` остаётся в профиле. Нет сетевых запросов каждый кадр.

Один HTTP200 не означает успех: endpoint batch может ответить `published=0` и errors. Адаптер удаляет только подтверждённые элементы, отклонённые сохраняет. Пустой/неоднозначный ответ оставляет очередь. Повтор после принятого запроса и аварии до записи подтверждения может доставить дубль — удалять по event_id. Это не обещание exactly-once. События, записанные через SDK.Data непосредственно перед аварийным закрытием, также зависят от завершения платформенного сохранения.

В Editor/Localhost/Unknown рабочая отправка выключена; Editor-пробы используют только отдельный временный профиль и локальный захват. Тестовая приёмка не должна попадать в производственную когорту; при будущем веб-тесте используйте тестовую ветку Cloud или фильтр попыток тестировщиков.

## Как считать уход

Начальное окно — **24 часа без продолжения** (настраиваемое правило отчёта). Сначала удалить дубли event_id и сгруппировать по content_version/attempt_id, а не по отдельной Cloud play session: refresh создаёт новую Cloud-сессию, но продолжает ту же попытку.

- Входы — уникальные attempt_id с enter; старые сохранения без telemetry не считать новичками.
- Конверсия этапа — уникальные попытки с completed данного step / уникальные попытки с started данного step. Resume не увеличивает числитель или знаменатель повторно.
- Победа, явный выход, retry и незавершённая попытка — отдельные исходы. Для retry старая попытка заканчивается повтором, новая начинается с нуля.
- Незавершённые попытки моложе24ч — «ещё ожидаем», не уход. После24ч — предполагаемый уход на последнем started/resumed этапе без completed (либо loading). Вернувшийся позже игрок пересчитывает результат.
- Сравнивать абсолютное число потерь, долю ухода и время на этапе; отдельно частоту смерти/возрождения. На малой выборке не объявлять причинность по одной корреляции.

События unload/quit не используются как доказательство ухода. Заблокированная аналитика, отсутствие сети и закрытие вкладки тоже могут выглядеть как потеря: отчёт отражает полученные данные.
