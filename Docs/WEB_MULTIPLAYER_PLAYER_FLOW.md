# Сценарий игрока: лобби, отправление и совместный забег

Статус: продуктовая спецификация для обсуждения, 2026-09-25. Основано на сценарии владельца игры и проверке текущего проекта. Сетевой кандидат — Photon Fusion 2.1 Shared, социальный слой — Mirra Cloud после отдельной проверки. Код игры пока не меняется.

## 1. Вход и видимое лобби

Игроку сразу предлагается «Играть одному»; параллельно игра пытается подключиться к Photon. **100 CCU — лимит выбранного бесплатного тарифа, а не правило игрового лобби:** вход в онлайн удаётся, пока есть доступная общая ёмкость Photon. При отказе Photon, превышении CCU или недоступной сети срабатывает существующий solo flow. Если Mirra социальный сервис недоступен, но Fusion работает, возможен вход в лобби без чата/друзей с явным статусом — решение после проверки связки аккаунтов. При жёстком лимите 100 нельзя рассчитывать, что уже принятый игрок гарантированно переподключится из лобби в забег, когда освободившееся место успеет занять другой: для стабильного перехода нужен запас ёмкости и обработка отказа всей группы.

Видимое лобби — отдельная Fusion Shared Session со сценой и максимумом 10 участников. Из подходящих открытых комнат выбирается существующая. Если комната только одна, новые игроки занимают её до лимита. Если комнат несколько, выбирается комната с меньшим заполнением среди непустых с местами; равные варианты чередуются случайно. Новую комнату создаём только когда нет места либо нужно разместить группу вместе. Это **наше правило поверх Photon matchmaking**: встроенный `FillRoom` заполняет старые комнаты до конца, `SerialMatching` распределяет более ровно, а точную политику «сначала заполнить первую, позже выравнивать» реализуем через список комнат/сервис подбора с повтором при гонке за последнее место.

Игроки в лобби видят других игроков, их позицию/анимацию, имя и выбранный внешний вид. Физические взаимодействия, бой, предметы и общий инвентарь в лобби не синхронизируются. Само движение/анимации **уже являются сетевыми данными**, так что лобби всё равно потребляет CCU и трафик. Чат и список друзей идут через Mirra, не через игровой поток Fusion.

При приглашении друга проверяем свободные места для всей приглашённой группы. Если место есть в текущем лобби, друг присоединяется по ID комнаты. Если нет, всем участникам группы предлагается вместе перейти в другое лобби, где помещаются все; при отсутствии такого создаётся новое публичное лобби и игроки переходят туда. Новый лобби с двумя друзьями потом может заселяться другими. Для знакомства без посторонних понадобится отдельный режим частного лобби. Переход должен сохранить party и чат связи между друзьями.

## 2. Точка отправления и сбор экипажа

Точка отправления в сцене открывает UI с двумя действиями: «Присоединиться» к ожидающему экипажу либо «Создать отправление». Стоять физически на точке после открытия UI постоянно не обязательно; важно подтвердить выбор. Сейчас `LobbyManager.StartGame()` запускает одиночный уровень напрямую — станции и список отправлений пока отсутствуют.

Создатель выбирает уровень, **желаемый размер экипажа от 1 до 4** и доступ: «Все» или «Только друзья». Выбранный уровень, желаемый размер, лидер, участники, видимость, статус и время старта хранятся как состояние отправления. После создания игроки переходят в отдельную Session ожидания/забега с соответствующим лимитом; готовые игроки видят состав и могут отменить ожидание. Когда набран выбранный размер, начинается общий сетевой обратный отсчёт. Пока набрано меньше, **лидер может нажать «Запустить сразу»**: текущий состав фиксируется и начинается тот же отсчёт, даже если в экипаже один человек. По окончании текущий master загружает уровень **в этой же Session**, чтобы не создавать лишнее переподключение. После фиксации состава новые участники уже не входят, только прежние могут вернуться после обрыва.

Для публичных отправлений рекомендуем поиск **среди всех лобби одного региона и версии**, а не только среди людей рядом с точкой: иначе экипажи по 2 человека в разных лобби никогда не наберут 4. Fusion может публиковать ожидающие Sessions с фильтрами `type=departure`, `level`, `public`, `version` и разрешать вход в комнату со свободными местами. Если игроки должны непременно видеть ожидающих рядом в текущем лобби, UI может сначала показывать местные отправления, затем — общие. Для «Только друзья» отправление скрыто из публичного поиска; приглашённые получают ID Session. Скрытие комнаты и случайный ID не являются полноценной проверкой дружбы: для строгого ограничения нужен серверный допуск/проверка состава или признание, что приватность держится на секретности приглашения.

Предлагаемые правила отказов: пока ожидание не закончилось, лидер может отменить отправление; если лидер вышел, роль передаётся одному из ожидающих; при уходе участника во время отсчёта таймер отменяется и ожидание состава начинается снова. Если до нажатия «Запустить сразу» в Session уже успел войти новый участник, запускается фактически находящийся там состав — кнопку нельзя использовать, чтобы выбросить этого игрока. После начала уровня случайные новые игроки не подключаются; только прежние участники возвращаются через reconnect в ограниченном окне.

## 3. Совместный забег

В забеге до четырёх игроков; все видят друг друга, анимации, оружие и действия. Общие поезд/корабль, топливо, локации, предметы, враги и босс имеют единое сетевое состояние. Master client принимает решения об общем мире, остальные передают действия и показывают результат. Лидер экипажа может отличаться от master client. Выход master требует передачи authority и продолжения состояния; браузер, зависший в фоне, требует watchdog и запроса смены master.

Когда босс побеждён, **один раз** фиксируется победа run ID, и каждому участнику показывается экран победы. Игроки выходят отдельно; оставшиеся видят тот же завершённый забег. Награду каждому участнику начисляем не более одного раза по паре `run ID + player ID`. При Shared Mode браузер master не является доверенным источником для ценной валюты; правила постоянных наград нужно проверить через backend. Игрок, покинувший забег до победы, по умолчанию не получает победную награду. Игрок, временно погибший, но остающийся в забеге, получает общий результат после победы — это предполагаемая трактовка «все выигрывают».

## 4. Животные на корабле и за игроком

Сейчас выбранные животные создаются `AnimalLoadoutBoardSpawner` **на трёх точках корабля** из локального `EggFeatureStorage`; `EggAnimalBuffService` локально применяет их бонусы в том числе к скорости/топливу корабля. **Решение: бонусы животных всех участников для общего корабля складываются.** Текущий `AnimalRunBuffs.Add` складывает плоские прибавки и перемножает множители; эту же семантику используем для общего набора корабельных бонусов, который authority рассчитывает по выбранным животным участников и фиксирует на старте забега. Личные бонусы к здоровью/движению остаются у владельца. Значения надо проверить на балансе при четырёх игроках, но автоматический верхний предел пока не вводим.

Предложение для новой визуальной механики: до трёх **миниатюрных животных каждого игрока** летят за ним цепочкой по истории его перемещения, с небольшим вертикальным покачиванием и отступом между звеньями. Их `animalId`, стадия и порядок входят в сетевое состояние игрока. Координаты каждого животного каждый сетевой тик **не передаём**: клиенты воспроизводят цепочку из уже полученного движения игрока и одинаковых параметров. При телепорте, переходе сцены или сдвиге `FixCoordinate` след сбрасывается/перестраивается. Животные на первом этапе декоративны: без коллизий, урона и самостоятельных взаимодействий. Их прежние баффы не должны зависеть от того, где визуально стоит модель. Можно оставить корабельные модели только как точки настройки до отправления, а в забеге показывать миниатюрных спутников.

## 5. Смерть, возрождение и реклама

Смерть — **личное состояние игрока**, не поражение всего экипажа. Погибший может посмотреть rewarded рекламу и возродиться, пока общий забег ещё идёт; остальные в это время продолжают играть. Если все игроки погибли и окно возрождения истекло, забег завершается поражением. После победы босса просмотр рекламы для возрождения уже не нужен.

Любой показ рекламы во время забега включает для конкретного игрока временную защиту от урона: с момента начала открытия рекламы до закрытия **плюс 1 секунда**. Сначала клиент запрашивает защиту и ждёт подтверждения authority, затем открывает рекламу — иначе игрок может погибнуть между нажатием и доставкой сетевого состояния. Общий мир и остальные игроки не ставятся на паузу. Во время рекламы игрок не атакует, не подбирает предметы и не управляет кораблём; если был водителем, управление освобождается. Защита хранится в сетевом состоянии игрока и учитывается тем, кто рассчитывает урон. Нужны предельная длительность защитного окна и очистка при ошибке/выходе/разрыве связи, иначе клиент может удерживать бессмертие бесконечно; предел выставляется выше реальной длительности объявлений на каждой площадке. Сохранность наград за рекламу требует проверки возможностей рекламной площадки: клиентский `success` сам по себе не доказывает просмотр.

**Что есть в коде сейчас:** `EndGameUIManager` вызывает `ShowRewardedAd("revive")` и `PlayerStatsManager.Revive()` локально. `PlayerStatsManager.TakeDamage()` и `Dead()` тоже локальны. `AdsManager` имеет общий вызов rewarded рекламы, но события начала/закрытия различаются у провайдеров. `MirraSDKAdsProvider` и `PauseProvider` используют `Time.timeScale = 0` для рекламы; в кооперативном режиме эта пауза не может быть способом защиты, потому что у остальных игроков время идёт. Нужно выделить общий жизненный цикл рекламы `requested/opened/closed/failed` для всех провайдеров, отделить локальную блокировку ввода/звука от сетевого статуса `AdProtectedUntil`, а возрождение подтверждать authority.

## 6. Обязательные проверки до переноса контента

1. Автоподбор: сначала одна комната заполняется до 10, затем несколько существующих выравниваются; приглашение друга из полной комнаты переводит группу вместе.
2. Отправление: публичный набор 1–4 человек из разных лобби, friends-only приглашение, общий отсчёт при полном составе, «Запустить сразу» с 1–3 участниками, уход лидера, отмена и повторное заполнение.
3. Животные: два игрока с разными loadout видят правильные миниатюры и **одинаковые** параметры корабля; 4 × 3 животных не ухудшают WebGL кадр заметно.
4. Реклама: игрок жив при показе, не наносит урон и не удерживает управление; после закрытия защита длится 1 секунду; ошибка или зависшее объявление снимает защиту по пределу. Другие клиенты продолжают забег.
5. Победа: смерть/реклама одного игрока не останавливает бой; после убийства босса результат и награда возникают один раз у каждого; выход игроков по отдельности не обнуляет сцену оставшимся.

## Принятые и оставшиеся правила

- Принято: бонусы животных всех участников для общего корабля складываются; личные бонусы действуют на владельца. Набор общего корабля фиксируется на старте забега.
- Принято: при неполном составе лидер может нажать «Запустить сразу»; в забег отправляется фактический состав от 1 до 4 человек.
- Должен ли погибший на момент убийства босса получить общую награду? Рекомендация: да, если он ещё участник Session; ушедший до победы — нет.
- После победы и выхода части игроков сколько времени показывать сцену остальным? Рекомендация: ограниченный послематчевый таймер с возможностью выйти сразу.
