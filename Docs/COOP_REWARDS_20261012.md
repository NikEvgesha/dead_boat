# Постоянная награда за совместную победу — DB-ON-021

## Что реализовано

- `EndGameUIManager` передаёт победу в `GameManager.GrantVictoryReward`. Обычный одиночный забег использует прежние `SaveWin` и `AddReward`.
- Сетевой забег начисляет **одну победу и кристаллы**, вычисленные прежним `ProfessionService.ApplyWinGemsReward(_reward)`. Клиент принимает сетевой `RunWon`; мастер устанавливает его при своём событии победы. Реплика не начисляет награду по одному локальному событию до общего результата.
- Ключ выдачи: исходное имя комнаты + стабильный Fusion PlayerUniqueId. Соло-ветка использует сохранённые `SourceRun` и `PlayerId`, поэтому повтор той же победы не создаёт новый ключ.
- Игровой `MirraSDKSaveProvider` хранит баланс, число побед и список полученных наград **одним объектом** `DeadBoat.RewardWallet.v1` через штатный Mirra SDK. При первой миграции подхватываются прежние `Gems` и `Wins`; остальные данные не меняются. Последующие изменения кристаллов/побед обновляют этот объект.
- UI получает итоговый баланс без второго `AddCurrency`; явно сохраняется постоянный провайдер. Временный онлайн-провайдер продолжает изолировать дистанцию, мир и инвентарь.
- Повторная выдача не изменяет баланс даже после более поздних покупок/начислений. Отметки не удаляются автоматически. При неподдерживаемом провайдере нет обхода через обычную соло-выдачу.

Это касается награды в существующем экране победы: кристаллов и счётчика побед. Достижения, их отдельные награды и разблокировки карт не включены в этот протокол. Их текущие сетевые записи остаются изолированными.

## Проверено ИИ

Unity 6000.3.9f1, проект dead_boat; новые методы найдены в загруженной сборке. `SharedRewardProbe.Run` выполнен через reflection вне главного потока:

- первая награда меняет кристаллы и победы;
- сериализация/новый экземпляр через Unity JsonUtility сохраняет отметку;
- повтор того же исходного забега/игрока с другим размером награды отклоняется;
- позднее изменение баланса не перезаписывается повтором;
- другой игрок и другой забег имеют отдельные ключи;
- победа с нулём кристаллов увеличивает число побед;
- некорректный ID/отрицательная награда/переполнение/неизвестная версия не создают частичное начисление.

Это проверка модели, **не** проверка записи в Яндекс-аккаунт или полноценного боя двух WebGL-клиентов. Изоляция Editor-сохранения поддерживает награды в памяти и не передаёт их провайдеру владельца. Обновление лидербордов также пропускается при изолированном провайдере.

### Игровой прогон после восстановления Unity

`SharedRewardGameplayProbe` — PASS: реальная загрузка Forest, настоящий босс через текущий damage-протокол, RunWon у обоих Fusion peers, экран победы локального игрока, постоянный провайдер теста получил ровно одну награду/победу, UI показал итоговый баланс. Повтор Win и прямой повтор GrantVictoryReward не увеличили баланс. После выхода локального игрока транспортный товарищ остался подключённым, получил authority и сохранил RunWon. Реальный маршрут выдачи SoloRunBranch с прежними SourceRun/PlayerId отклонил вторую награду даже с другим размером.

Провайдер постоянного сохранения в этом прогоне изолирован и хранит результат в памяти. Соло-маршрут проверен созданием объекта ветки с исходными ID, без повторения её полного загрузчика/восстановления мира (отдельные проверки DB-ON-026). Это один игровой мир и один транспортный peer, не два полноценных WebGL клиента.

Предыдущие попытки не засчитаны: искусственный прыжок лодки с игроками в городе создал слишком широкий участок мира и переполнил Fusion allocator; затем запуск напрямую из Lobby пропустил boot; затем транспортный клиент не отправил BoatProfile. Исправлен именно harness: явный boot, совместный перенос и диапазон хранения у босса, сообщение BoatProfile. Итоговый прогон прошёл; переполнение при большом расхождении игроков остаётся риском стресс-проверки, не доказательством достаточной оптимизации.

## Ограничения и решение о доверии

Выдача через этот адаптер включена только в Editor и сборках с `DEADBOAT_MIRRA_DIAGNOSTICS` (наш тестовый черновик). В остальных сборках возвращается `RequiresServer`, без обхода через обычную соло-выдачу. Это намеренный барьер до серверного claim, а не готовая поддержка релиза.

Это клиентский пилот. Photon Shared передаёт вердикт браузера master; он не доказывает победу доверенному серверу. Нельзя считать данный механизм защитой ценной валюты от подделки.

В штатном `IDataContainer` установленного Mirra SDK 5.1.20 сохранение имеет вид `void Save()`. WebGL-мост вызывает `Module.mirraSDK.data.save()` без передачи подтверждения результата в C#. Один объект предотвращает разделение баланса и отметки на разные игровые ключи; **гарантия атомарной серверной записи, подтверждённой доставки и слияния нескольких устройств не проверена**. При откате/удалении сохранения защиты от повторной выдачи нет. Несколько вкладок могут перезаписать сохранения друг друга. Старый билд после миграции читает устаревшие ключи Gems/Wins; тестировать старые и новые билды на одном аккаунте нельзя считать совместимым обновлением.

Серверный следующий этап: идемпотентный claim по `account + run + participant`, серверная проверка результата и атомарная операция изменения кошелька/отметки; повтор запроса возвращает прежний результат. Сервисные секреты должны находиться на сервере. Cloud Code не используем по рекомендации Mirra. До доступности такого сервиса пилот не считается готовым защищённым начислением для публичного релиза.

## Следующие шаги

1. **ИИ:** подготовить новую тестовую WebGL-сборку с уже прошедшими Editor-проверками.
2. **Владелец:** два клиента, победа, сравнить баланс/счётчик после выхода и перезагрузки; один выходит раньше другого; соло-ветка использует исходный ключ. Текущая сборка возврата не содержит этих новых правок.
3. **ИИ + внешняя команда:** согласовать доступный доверенный backend для выдачи, проверить подтверждение сохранения и конкурентные записи. Без отдельного запроса обратную связь Mirra не отправлять.
