# Чат Mirra для онлайн-лобби — пилот

Дата: 2026-10-06. DB-ON-012 / DB-ON-013. SDK v0.10.0 не изменён.

## Что реализовано

- MirraLobbyChat использует общий SDK MirraSocialService. Работает только в общем онлайн-лобби, не в каталоге, комнате отправления, одиночном режиме или забеге.
- Master Client создаёт room-канал из шаблона. Только `channelId` передаётся через Photon Session Property `mc_chat_v1`; сообщения хранятся и доставляются Mirra. Имя канала не используется как идентификатор. Это публичный чат, не проверка допуска для приватного экипажа.
- Клиент Join → Connect → Subscribe → загрузка последних 50 сообщений. После восстановления подписки история перечитывается. При смене комнаты выполняются Unsubscribe/Leave/Disconnect; общий semaphore разделяет teardown старого компонента и подключение нового.
- Создатель уже является участником после CreateChannel, повторный Join не нужен. Для отказа Join с HTTP 409 членство проверяется через GetMembers и SelectedProfileId; нельзя считать любой конфликт успешным входом.
- Порядок по Number, дедупликация по MessageId, версии правок по EditedAt/CreatedAt. Tombstone не даёт старому ответу истории вернуть недавно удалённое сообщение. Хранится 50 сообщений и до 200 tombstone на текущее подключение.
- Текст максимум 200 символов; отправки разделены двумя секундами после завершения запроса. Неудачная отправка не повторяется автоматически, текст остаётся в поле. Перед отправкой вызывается ProfanityFilter.CheckAsync; отказ/недоступность проверки запрещает отправку.
- UGUI окно со скроллом, безопасным plain text и полем ввода. Пока вместо подтверждённых ников показана короткая метка отправителя. Набор текста сбрасывает таймер бездействия. PlayerInput игнорирует игровые действия при фокусе UGUI InputField.

## Почему пока выключено

`Assets/Resources/OnlineUI/MirraLobbyChatSettings.asset`: `enabledForPilot=false`. Настройки шаблона Cloud и обязательная серверная модерация ещё не проверены. В текущей сессии Hub перенаправил на вход; владелец получил просьбу войти. Ключи `deadboat-lobby-v1` и `deadboat-chat` — предложенные имена, а не подтверждённые объекты проекта.

Клиентский CheckAsync можно обойти изменённым клиентом. Поэтому перед включением нужны доказанные серверные проверки при отправке и редактировании сообщения, rate limit и политика доступа. Переключатель игры не обеспечивает эти проверки.

## Отдельная игровая сборка чата

`MirraCloudSmokeBuild.QueueGameChatPilot()` собирает включённые игровые сцены в `Builds/MirraGameChatPilot`. Это изоляция тестового пространства, не аутентификация/секрет и не серверная защита от спама. Опубликованный архив с этой define не предназначен для общего доступа.

Запуск локально: `python tools/online-webgl/serve_smoke.py --build MirraGameChatPilot --port 8767`; второй клиент — отдельный origin на порту 8768. Гостевые хранилища этих origin независимы.

### Приёмка двух игровых клиентов (частично проверена ИИ, приёмка владельцем впереди)

1. A и B выбирают онлайн, оказываются в одном лобби; сообщения видны обоим. Проверить локальное скрытие B на A и обратное включение.
2. A выходит из онлайн-лобби. B становится Photon master; существующий Cloud channel/история остаются, B может писать. A возвращается в непустое лобби и читает прежнюю историю.
3. Два игрока создают экипаж, отправляются в общий забег. Чат общего лобби закрывается/отписывается; прежние сообщения не попадают в UI забега.

### Реальные сцены и fallback истории 2026-10-07

На двух игровых WebGL origin проверен обычный поток через GameStartPoint: каталог → создание/вступление в экипаж на 2 места → автоматический старт → стартовый город общего забега (connected, players:2, одинаковый сид/версия генератора) → независимый выход каждого через меню → общий чат вернувшихся игроков. После первого выхода второй оставался в забеге с players:1. Chat UI отсутствовал в каталоге и забеге; после возвращения появился чат нового непустого лобби. Сообщение A после возвращения было видно B. Это проверка начала и возврата из забега, не его прохождения до босса. Сетевой teardown Cloud непосредственно не принят: запись CDP truncated. Скриншот Builds/MirraChatSceneReturn-20261007.png.

Повторён пропуск live ответа B на A; ручное закрытие/открытие чата восстановило сообщение из REST. Добавлен таймер сверки: раз в 15 сек только при открытой панели, Application.isFocused и chat.Ready, с существующей защитой RefreshHistory от параллельных запросов и cooldown 10 сек. Это до 4 периодических запросов последних 50 сообщений в минуту на активную открытую панель, плюс запросы открытия/фокуса с общим cooldown. При закрытой панели/забеге/офлайне таймер не опрашивает Cloud. Основной путь остаётся WebSocket; REST уменьшает последствия пропуска, но не даёт гарантии доставки при отказе сервиса/сети.

Во время восстановления прежний буфер не очищается до ответа. Live события за время запроса копятся до 50 различных сообщений и применяются после snapshot; stale edit отбрасывается, tombstones удалений сохраняются до смены комнаты. Применение snapshot вызывает один refresh UI, а не по каждой записи. При ошибке REST работает существующий retry. SDK без правок.
