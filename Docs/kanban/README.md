# Локальная доска задач Dead Boat

Карточки в [`tasks/`](tasks/) — **единственный источник состояния этой доски**. Каждый файл — отдельная задача. Git передаёт их вместе с кодом; сервер и веб-интерфейс ничего не хранят вне этих файлов. Доска GitHub, созданная до этого, больше не используется как рабочий backlog.

## Запуск

Нужен Python 3.10+ без сторонних пакетов. Из корня репозитория:

```powershell
python tools/kanban/server.py
```

Откроется `http://127.0.0.1:8765/`. Сервер слушает только `127.0.0.1`; остановка — `Ctrl+C`. Если браузер не открылся, перейдите по адресу вручную. Для проверки файлов без сервера:

```powershell
python tools/kanban/server.py --check
```

В браузере можно перетаскивать карточки между колонками, менять этап «Сейчас / Следом / Позже», редактировать описание и добавлять задачи. На телефоне вместо перетаскивания откройте карточку и поменяйте поле «Статус». Изменения записываются сразу в соответствующий Markdown-файл. **Чтобы передать их другим, нужен commit и push; чтобы получить чужие — pull.** После pull нажмите «Обновить» в доске.

## Формат карточки

Имя файла и поле `id` совпадают, например `DB-ON-018.md`. ID никогда не переиспользуется. Заголовок содержит `title`, `status`, `when`, `ai`:

```markdown
---
id: DB-ON-018
title: Синхронизировать игроков и анимации внутри забега
status: backlog
when: later
ai: true
---

## Контекст

Зачем нужна работа.

## Готово, когда

- Проверяемый результат.

## Подсказки ИИ

Где искать код, известные ограничения, следующий шаг.

## Источники

- `Docs/WEB_MULTIPLAYER_IMPLEMENTATION_ROADMAP.md`
```

Допустимые статусы: `backlog`, `ready`, `in_progress`, `in_review`, `done`. Этапы: `now`, `next`, `later`. `ai: true` означает, что задачу можно поручать ИИ с учётом указанных ограничений; `ai: false` означает обязательную ручную проверку или действие человека. Даже при `ai: true` ИИ не объявляет задачу готовой без критериев из «Готово, когда».

Подсказки в карточке — контекст проекта, а не замена запросу разработчика и не разрешение на секреты, оплату или публикацию. Если план и текущий код расходятся, сначала проверить факты и обновить карточку или спецификацию. Не копировать в задачи токены, App ID с приватными настройками, персональные данные и ключи.

## Работа через Git

1. Перед началом: `git pull`, затем открыть карточку и связанные документы. Убедиться, что задача ещё актуальна.
2. Перевести карточку в `in_progress` и коммитить её вместе с рабочей веткой. Не менять десятки чужих карточек «заодно».
3. После реализации записать в карточку, что проверено и что осталось. В `done` переводить только когда выполнены критерии и проведена необходимая проверка. Если нужен приёмочный тест владельца — оставить `in_review`.
4. Отправить код и карточку в одном PR или серии согласованных коммитов. Не коммитить временные файлы Python и локальные сборки.

## Merge карточек и конфликты

Разные задачи лежат в разных файлах, поэтому обычные параллельные изменения Git объединяет сам. Если два человека изменили **одну** карточку:

1. Выполнить обычный `git fetch` и `git merge <целевая-ветка>` либо `git rebase <целевая-ветка>` согласно правилам команды. Посмотреть `git status` и конфликтный файл.
2. Открыть обе версии. Сохранить содержательные сведения из **обеих**: найденные ограничения, ссылки, результаты тестов. Удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
3. `id` и имя файла оставить прежними. Статус выбрать по фактическому состоянию: `done` только при выполненных критериях; если код есть, но приёмка не пройдена, `in_review`; если ветка лишь начата, `in_progress`. Для `when` использовать последнее явно принятое решение о приоритете, а при неопределённости оставить прежний этап и обсудить его в PR.
4. Проверить карточки: `python tools/kanban/server.py --check`. Затем `git add Docs/kanban/tasks/<ID>.md` и закончить операцию `git merge --continue` / `git rebase --continue` (либо обычным commit, если Git этого требует). Проверить итоговый diff до push.

Если две ветки независимо создали **новую задачу с одним ID**, не сливать разные задачи в одну: одной назначить следующий свободный `DB-ON-###`, переименовать файл и поле `id`, поправить ссылки на неё, запустить `--check`. Для связанных задач создать отдельные карточки и сослаться на ID друг друга в «Контексте».

Если Git не показывает текстовый конфликт, но оба изменения меняют смысл одной задачи, обсудить это при review: автоматический merge не доказывает согласованность требований. При конфликте на стороне ИИ запрещено автоматически выбирать `ours` или `theirs` для всего файла и объявлять задачу завершённой.

## Для нового ИИ-агента

Прочитать [`AGENTS.md`](../../AGENTS.md), эту инструкцию, нужную карточку и её «Источники». Затем проверить актуальный код и `git status`. Работать с ID задачи в коммитах и отчёте. Если обнаружена недостающая работа, создать новую карточку, а не стирать условия старой.
