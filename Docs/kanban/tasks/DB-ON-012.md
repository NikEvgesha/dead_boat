## Контекст

В каждом лобби до 10 игроков нужен текстовый чат для знакомства.

## Готово, когда

- Сообщения видны участникам комнаты в правильном порядке.
- Есть ограничения длины и частоты.
- Недоступность чата не закрывает вход в игру.

## Подсказки ИИ

Выбрать сервис после проверки Mirra Cloud; не использовать Fusion state как долговременное хранилище сообщений.

## Источники

- `Docs/WEB_MULTIPLAYER_PLAYER_FLOW.md`
- `Docs/WEB_MULTIPLAYER_IMPLEMENTATION_ROADMAP.md`

## Разбор SDK 2026-10-06

ChatsService v0.10.0 имеет REST историю и WebSocket-подписку. CreateChannelAsync требует заранее созданный шаблон (templateKey). В игре появился общий владелец SDK MirraSocialService (DB-ON-010), но chat UI/создание/подписка пока не реализованы. Следующий шаг — ИИ: проверить шаблон и доступ участников в Dead Boat Cloud, затем хранить channelId в Photon-комнате и ограничить историю/частоту отправки. Не создавать отдельный канал каждым клиентом по одинаковому имени.


## Реализация 2026-10-06

Добавлены MirraLobbyChat, LobbyChatUI и ресурс настроек. Master создаёт канал из templateKey и публикует channelId в Session Property; клиенты вступают, подписываются, читают 50 последних сообщений. Есть teardown переходов, восстановление истории после reconnect, версии правок/удалений, лимит 200 символов и интервал отправки 2 секунды. Ввод в UGUI InputField подавляет игровые горячие клавиши. Локальные проверки буфера и C# компиляция прошли.

Пилот ВЫКЛЮЧЕН: Hub просит вход, шаблон/серверная цензура/CSP WebSocket не проверены. Полное описание и приёмка: `Docs/MIRRA_LOBBY_CHAT_PILOT.md`. Следующий шаг: владелец — вход в Mirra Hub; ИИ — настройки и безопасный тест двух клиентов. Архив/черновик не обновляли, SDK не меняли.

## Проверка Cloud 2026-10-07

Владелец вошёл в Hub. В проекте Dead Boat включены сервисы Чаты и Цензура, создан шаблон `deadboat-lobby-v1` (Dead Boat Lobby) с группой `deadboat-chat` (Dead Boat Lobby Chat). В группе включены словари ru/en и нечёткое сопоставление. Подсказка Hub обещает маскирование слов группы; фактическая проверка приведена ниже.

Unity 6000.3.9f1, штатный Cloud SDK v0.10.0: в отдельном канале SDK self-test выполнены Create → Connect → Subscribe → Send → Edit → GetMessages, без ProfanityFilter.CheckAsync. Отправка английского тестового запрещённого слова и правка на русское завершились успешно; ответы содержали непустой очищенный текст без исходных запрещённых слов. История содержала сообщение без этих слов. Итог: sendSuccess=True, sendProtected=True, editSuccess=True, editProtected=True, historyProtected=True. Затем выполнены Unsubscribe/Leave/Disconnect, Play Mode остановлен. Этот тест подтверждает серверное маскирование двух примеров, не полноту словарей/защиту от всех обходов.

Пилот остаётся выключенным. Два независимых клиента, браузерный WebSocket/CSP, серверный rate limit, жалобы/mute и retention ещё не проверены. На форме шаблона видны только ключ, имя и группа фильтра; отсутствие там лимитов не доказывает отсутствие серверных ограничений. SDK не изменён, новая сборка/загрузка черновика не выполнялась.

Следующий шаг — ИИ: проверить доставку между двумя независимыми тестовыми клиентами в WebGL и доступный серверный путь ограничения спама. После подготовки сборки — владелец: приёмка UI и обмена сообщениями в тестовом черновике. Вход в Hub больше не ожидается.

## Два клиента WebGL 2026-10-07

Собрана отдельная сцена `Assets/Online/SmokeTest/MirraChatWebGLProbe.unity` с define DEADBOAT_MIRRA_CHAT_PROBE. Штатный SDK, без API токена. Кнопки диагностического клиента создают/вступают только в отдельный self-test канал; посылаются безопасные технические сообщения. Серверы слушали loopback на портах 8767 и 8768: отдельные origin и хранилища гостя.

Фактически прошли: Create у A, Join/Connect/Subscribe у B; live событие сообщения B→A (#1), A→B (#2); GetMessages у B вернул 2 сообщения. После перезагрузки B повторный Join/Connect прошёл, новое сообщение B дошло до A (#3). Это проверка Cloud SDK WebGL и восстановления страницы, не приёмка игрового UI/Photon-привязки/автоматического reconnect при потере сети. Адрес реального сокета: `wss://sdk.mirracloud.com`, без query и токена. CSP Яндекса локальная страница не проверяет.

Выявлен отказ штатного DisconnectAsync: при выходе WebGL UI оставался busy. По исходникам ChatsService после синхронного завершения внутреннего Disconnect подписывает UseCompleted слишком поздно; callback уже не вызывается. Дополнительно воспроизведено в Unity при уже закрытом соединении: rawCompleted=False, state=Disconnected.

В игровом коде добавлен MirraChatConnection: вызывает штатный DisconnectAsync и ждёт завершения либо подтверждённого ConnectionState=Disconnected, не дольше 5 секунд по realtime. Применён к teardown MirraLobbyChat и диагностике. Проверка Unity: rawCompleted=False; adapterCompleted=True; state=Disconnected. Изменённые скрипты импортированы без ошибок. SDK не менялся. Текущий локальный WebGL-артефакт собран ДО этой правки; повторная WebGL-проверка исправленного выхода ещё нужна.

Игровой пилот остаётся выключенным. Следующий шаг ИИ: собрать обновлённый probe, проверить graceful Leave/Disconnect→Join и CSP черновика (Консоль при первом просмотре показывала Failed to fetch). Требования серверного антиспама/жалоб/retention: `Docs/MIRRA_CHAT_SERVER_REQUIREMENTS.md`; владелец при необходимости передаёт вопросы команде Mirra, которая подтверждает гарантии. Загрузка/публикация игрового черновика не выполнялась.

Дополнение CSP 2026-10-07: после «Повторить» Яндекс Консоль загрузилась. На вкладке CSP → «Текущий список хостов» для 424778 подтверждён sdk.mirracloud.com, рядом с exitgames.com/photonengine.io. Новая заявка не отправлялась, настройки не изменялись. Это доказательство регистрации хоста в Консоли; реальное WSS-подключение из игрового iframe и UI пилота пока не проверены. Предыдущее Failed to fetch оказалось временным, не текущим блокером доступа.


## Проверка применяемой CSP 2026-10-07

Это подтверждение разрешённого адреса, пока не доказательство реальной доставки чата из Яндекса. Проверено фактически:

- A: Join/Connect/Subscribe из Яндекса; Send в обе стороны. A получил live сообщения B (#2, #3), B получил live сообщение A (#4). GetMessages у обоих вернул 2 сообщения на первом чтении.
