## Готово, когда

### Исправление и реальный тест 2026-10-08

Двухпрофильный runtime-тест опроверг предположение ниже о необходимости AccountId: GetProfileAsync чужого SenderId возвращает HTTP 404, а Friends.SendAsync с самим серверным SenderId — HTTP 204. Свой профиль читается (HTTP 200). Игровой адаптер теперь отправляет SenderId напрямую; собственный ID для копирования в «Друзьях» — SelectedProfileId. Кэш и промежуточный GetProfile удалены. Проверка себя учитывает и account ID, и selected profile ID.

MirraFriendsRuntimeProbe в изолированной Play Mode сцене со штатным SDK 0.10.0 прошёл: два новых гостевых аккаунта, сообщение в отдельном канале, заявка через игровой адаптер, входящая заявка, принятие, восстановление того же аккаунта из памяти, сохранённая дружба и удаление. Проверены запрет себя/повторной заявки. Временные credentials хранятся только в памяти; отношения удалены, участники вышли из тестового канала. Это реальный Cloud тест в Editor, а не доказательство WebGL UI или межплатформенного входа. SDK не менялся.

WebGL-пилот собран: `Builds/DeadBoatChatPilot-20261008.zip`. В двух локальных игровых клиентах на разных origins проверены сообщение B, заявка A из чата, входящая у B, принятие, дружба у обоих и сохранность тех же профилей/дружбы после перезагрузки обоих страниц. Кнопка у автора собственного сообщения «Это вы», у отправителя после заявки «Заявка отправлена» и недоступна. Скриншоты в Builds: MirraChatFriendRequest-20261008.png и MirraFriendsRestored-20261008.png. Локальный стенд отключает pointer lock только в HTTP-ответе: FPS-ввод этим тестом не принят, в ZIP стенд не входит. Яндекс-черновик не заменялся.

Следующий шаг — владелец: приёмка новой кнопки и повторного входа на двух профилях в Яндекс-черновике; статус остаётся in_review. ИИ: дальше DB-ON-011, доставка приглашения и согласованный переход друзей в лобби, включая заполненную комнату.

После WebGL проверки удаление другом B выполнено через UI; после обновления оба списка пусты. Тестовые вкладки и два локальных HTTP сервера закрыты. Межустройственное восстановление гостевого профиля этим тестом не подтверждено.

### Дополнение 2026-10-08: запрос из чата

По запросу владельца добавлена кнопка «В друзья» для выбранного автора сообщений в LobbyChatUI. SenderId не берётся из текста/метаданных. Штатный SDK Chats использует профили, Friends использует аккаунты: RequestChatFriendAsync читает GetProfileAsync(SenderId), проверяет совпадение Id и отправляет Friends.SendAsync(AccountId). Своя выбранная персона, существующий друг и известные входящие/исходящие заявки отключают кнопку. Во время запроса кнопка занята, есть 2-секундная пауза и ограниченный кэш 50 соответствий. При смене/окончании сессии результат профиля не отправляет заявку новому аккаунту. Результат отображается в чате; закрытая панель не получает запоздалый результат.

Компиляция в Unity dead_boat и MirraChatValidation PASS (включая отсутствие HTTP от недоступной кнопки, прежние buffer/lifecycle/hide проверки). EditMode стенд использует отдельный неавторизованный социальный компонент, не создаёт постоянную игровую сессию. Реальное GetProfileAsync другого игрока → Friends.SendAsync(AccountId) и новая WebGL кнопка ещё не проверены двумя профилями. Статус in_review сохраняется. Сборка/черновик не обновлялись, SDK не менялся.

Следующий шаг — ИИ: собрать пилот с кнопкой; владелец проверяет отправку из чата, принятие в «Друзьях», невозможность добавить себя/повторить заявку и сохранность после перезахода.

- Запрос/принятие/удаление работают после повторного входа.
- Состояние друзей согласовано между площадками, где это возможно.
- Ошибки сервиса отображаются без поломки solo.
