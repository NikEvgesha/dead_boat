# Проверка применимости Photon Fusion Shared

Дата: 2026-09-25. Решение на текущий момент: **Fusion 2.1 Shared — кандидат для WebGL-прототипа**, но не подтверждённый релизный стек до вертикального среза на целевых площадках. Это дополнение к [плану](WEB_MULTIPLAYER_PLAN.md) и [сравнению рантаймов](WEB_MULTIPLAYER_RUNTIME_OPTIONS.md). В стоимость разработки денежный бюджет не включает.

## Главное различие: Photon Lobby и наше игровое лобби

В Fusion `Lobby` — каталог игровых `Session`; находящиеся в этом каталоге пользователи не видят друг друга и не общаются. Наше видимое лобби на 10 человек должно быть **отдельной Fusion Shared Session** со сценой, аватарами и комнатным состоянием. Забег 1–4 игроков — **другая Shared Session** с ограничением `PlayerCount = 4`. На одном `NetworkRunner` клиент может находиться только в одной Session: переход лобби → забег → лобби требует выхода и входа, а состав группы должен пережить переход во внешнем social/backend состоянии. Mirra чат может работать параллельно, но его канал должен быть связан с ID комнаты и очищаться по правилам жизненного цикла комнаты.

## Как Photon считает пользователей

`PlayerCount` — максимальная вместимость одной Session, **не зарезервированные платные места**. Photon CCU считает реальные одновременные подключения к одному AppId во всех комнатах. Комната на 10 с двумя игроками даёт 2 CCU; забег на 4 с тремя игроками — 3 CCU; вместе — 5 CCU. Пустые места ничего не добавляют. Игрок, перешедший из лобби в забег, обычно остаётся одним подключённым пользователем, а не считается дважды; при переходе нужно уничтожить прежний `NetworkRunner` и создать новый. Если временно поддерживать два активных подключения, реальная метрика может быть выше, поэтому архитектурой избегаем такого перекрытия. Игрок в Fusion matchmaking Lobby, но уже подключённый к Photon, тоже занимает CCU. Настоящий offline/solo, не открывающий соединение с Photon, даёт 0 CCU.

Тариф Photon выбирается по *пиковым* CCU, причём месячные пики разных регионов суммируются для плана. Кроме CCU считается входящий и исходящий трафик. Бесплатный релизный Fusion-план ограничен 100 CCU и 0,3 ТБ/мес. без burst; при достижении лимита новые соединения отклоняются. [Правила CCU](https://doc.photonengine.com/photon/current/pricing), [тарифы Fusion](https://www.photonengine.com/Fusion/Pricing).

## Матрица требований

| Требование | Вердикт | Как реализовать и что проверить |
|---|---|---|
| WebGL на площадках | SDK поддерживает | Официальный Fusion WebGL sample на Unity 6 и Shared Mode существует. Проверить WSS/доступ к Photon из каждого publisher iframe, загрузку и фон вкладки. Unity Editor не заменяет эти проверки. |
| Автоматическое заселение многих лобби до 10 | SDK поддерживает основу | `GameMode.Shared`, `PlayerCount = 10`, `MatchmakingMode` и свойства с типом комнаты, регионом/языком/версией; при отсутствии подходящей Session создаётся новая. Лимит и гонку на последнее место проверять на нагрузке. |
| Единый ID друга в Mirra и игрока Photon | Нужен серверный мост | Анонимный или заявленный самим браузером `UserId` можно подменить. Нужна Custom Authentication: backend проверяет токен Mirra и отвечает на запрос Photon, назначая проверенный ID. Доступность такого сценария в Mirra проверить до реализации друзей и наград. |
| В лобби видны аватары и анимации | Да, интеграция наша | Отдельный local/remote player prefab, `NetworkObject`/`NetworkTransform`, компактные состояния анимации. Текущие singleton-скрипты игрока не должны запускаться на remote avatar. |
| Друзья, приглашения, чат, мат-фильтр | Внешний сервис | Mirra Cloud после подтверждения доступности и тарифа. Fusion Session принимает игрока по имени/коду; чат и друзья не являются функцией Fusion Shared. Серверная проверка чата обязательна. |
| Группа 1–4 с лидером | Логика наша | Временная party запись в backend с устойчивыми ID, лидер создаёт закрытую run Session, рассылает приглашение/имя Session, места резервируются или ограничиваются токеном допуска. Лидер группы не обязан быть master client. |
| Общий поезд, топливо, дистанция | Да, переделка игры | `NetworkObject` с `Is Master Client` и `[Networked]` состоянием; симуляция у текущего master, остальные отображают. После смены master логика читает состояние и продолжает без повторного спавна/обнуления. |
| Случайные локации и объекты | Да, переделка игры | Seed для декораций, стабильные ID и сетевой spawn/despawn для значимых объектов. Локальный `Random` каждого браузера не может решать судьбу предметов и врагов. |
| Предмет исчез у всех и попал одному | Да, переделка игры | Игрок шлёт запрос владельцу предмета/общего мира; тот проверяет расстояние, статус и атомарно назначает владельца. Текущее состояние предмета хранить в Networked state, а не только в RPC: это нужно для reconnect и позднего входа в лобби. |
| Враги, попадания, урон, боссы | Да, высокая трудоёмкость | AI и итоговое здоровье на master/владельце объекта; игроки отправляют действия, master подтверждает результат. Нужен выбор цели из четырёх игроков. Физику с взаимодействиями тестировать отдельно: Shared Mode допускает Forecast, но в его приближении позиции могут отличаться между клиентами. |
| Переход между сценами | SDK поддерживает | `NetworkRunner.LoadScene` вызывает master client. Из лобби в забег лучше переходить в отдельную Session; внутри забега уровни загружает текущий master. Все должны иметь одинаковую версию контента. |
| Выход master client | SDK поддерживает передачу роли; восстановление наше | Объекты с `Is Master Client` переходят новому master. Конкретно поезд, AI, спавны, таймеры и награды должны пережить смену. Объекты игрока/мира нельзя случайно уничтожить настройкой `Destroy When State Authority Leaves`. |
| Зависание master во вкладке | Условно | В Fusion 2.1 можно запросить смену неотвечающего master, но она **не происходит автоматически** до disconnect. Нужны heartbeat, один наблюдатель, порог, `RequestMasterClientReassign()` и тесты фона/сна вкладки. Возможна короткая пауза; нулевую паузу обещать нельзя. |
| Reconnect прежнего участника | SDK даёт пример; логика наша | Сохранять ID сессии и аватар на ограниченное время, разрешить перехват State Authority при возврате, восстановить инвентарь/позицию из сетевого состояния. Shared Mode не использует Client Host `ConnectionToken`; автоматический механизм `Connection Lost & Quick Reconnect` из документации Fusion относится только к Client/Server и Shared Mode не поддерживает. Если Session опустела или уже закрыта, прежний забег без внешнего сохранения не восстановить. |
| Офлайн и отказ подключения | Да, логика наша | До входа в Session — таймаут, ограниченный retry, возврат в существующий solo flow. Во время забега — reconnect или завершение; четыре независимых solo-копии одного мира недопустимы. |
| Безошибочные награды/античит | **Нет, одним Fusion Shared не обеспечить** | Master client — браузер игрока, который может отправлять ложное состояние. Для ценных валюты, покупок и постоянного прогресса нужны доверенный backend, серверная проверка результатов или отказ от начисления таких наград в ранней версии. Простая запись результата от master на сервер не является проверкой. |
| Мир продолжает жить без всех игроков | **Нет, без внешнего сервера/сохранения** | При пустой Session некому считать поезд и AI. Если забег должен переживать выход всей группы или жить часами в фоне, понадобится отдельный сервер и хранилище; Shared Mode не исполняет Unity симуляцию в Photon Cloud. |

## Специальные риски этого проекта

1. `PlayerManager`, `PlayerInput`, `PlayerMovement`, `Inventory` и связанные UI используют singleton. Добавить сетевой prefab как вторую копию нынешнего игрока нельзя: необходимо разделить локальный контроллер и удалённый аватар.
2. `BoardController` ведёт поезд в `FixedUpdate`, а `FixCoordinate` сдвигает начало сцены. Сетевое состояние должно хранить абсолютную дистанцию и глобальные позиции, чтобы новый master не применил сдвиг дважды.
3. `LocationSpawner`/`LocationContentSpawner`/`ZombieSpawner` используют локальный `Random`/`Instantiate`. Без сетевого каталога значимых объектов четыре клиента увидят разные предметы и врагов.
4. `ZombieController`/боссы рассчитаны на одну цель. Перед переносом контента нужно проверить одну базовую схватку с несколькими игроками.
5. `SaveManager` хранит персональное состояние. Solo-save, checkpoint конкретного run и постоянные награды надо разделить; для наград нельзя принимать только утверждение master client.

## Контрольный вертикальный срез до полной интеграции

Сначала внедрить SDK в изолированном checkout/ветке и собрать минимальную WebGL сцену. Не переносить сразу все уровни и системы. Срез считается успешным, когда:

1. На реальной целевой площадке 10 браузеров входят в видимое лобби; одиннадцатый открывает новое, а пользователь без сети заходит в solo.
2. Четыре игрока из party попадают в одну отдельную run Session; остальные остаются в лобби. Приглашение друга по ID переживает переход между Session.
3. Каждый видит чужое движение, анимацию и экипировку без чужой камеры/UI; четыре WebGL клиента сохраняют приемлемый FPS и трафик.
4. Один поезд, один предмет и один враг имеют одинаковое состояние у всех. Два игрока одновременно пытаются поднять предмет — он достаётся ровно одному. Поздний reconnect видит его уже поднятым.
5. Master закрывает вкладку, затем отдельным тестом уводит её в фон без отключения: поезд/враг продолжают после смены authority без дублирования предметов и наград.
6. Измерены p95 кадра, RTT, KiB/s на игрока, время смены master и reconnect. Предельные значения задаются после первого замера, до переноса остальных механик.
7. Отдельно решён вопрос постоянных наград: либо доверенная проверка на backend, либо на этом этапе кооператив не начисляет ценные результаты.

**Решение после среза:** если 1–4 выполняются, но пункт 5 нестабилен или требуется строгая серверная валидация всей экономики, рантайм забега следует перенести на выделенный сервер. Это решение надо принять до массовой сетевой переделки локаций и врагов.
